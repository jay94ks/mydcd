## CD 이력·원 값·서비스 변경점

User kind1의 `app-cd-history`·`app-cd-diff`는 Tenant와 전용 AppCDRead 선택자를 사용한다. history만 바깥 After를 허용하고 diff는 Part/Digest 고정 snapshot을 읽는다. 기존 app-cd-field의 선택 Part/Digest와 Values/ValuesPart가 같은 분할 수집을 사용한다. 같은 nonce/challenge/Session·현재 Read·quorum/leader relay를 유지하며 원문·provider 자격을 실행 권한으로 취급하지 않는다. [전체 메시지/값/이력 계약](../../reference/cd-inspection.md)을 따른다. field/diff의 큰 값은24KiB part와 전체 SHA-256으로 조립하고 변경된 snapshot은 conflict다. kind·schema 번호는1을 유지한다.

배포 Diff의 RQ5 optional `Replacement`는 같은 종료 closure 코어의 노드별 원 claim 목록이다. app-plan의 Diff 결과와 app-cd-diff의 기존 유한 part/digest 안에 포함하며 별도 wire kind나 비인증 실행 경로를 추가하지 않는다. 현재 tenant 권한으로 읽고 Targets의 Key/Generation/Revision을 혼합하지 않는다. 영향 계획을 native 종료·health·다음 노드 실행 권한으로 사용하지 않는다. [Unix API 형식](../../reference/unix-sockets.md)을 따른다.


RQ5 순차 교체는 기존 관리 `app-progress`에 `advance-wave` action을 사용한다. 활성 설치 WorkKey·원 operation/epoch/Inventory CAS·현재 원 사용자 grant를 확인하고, 같은 Inventory의 원 종료 증명 및 새 세대의 신선한 health로만 다음 노드를 진행한다. User/Unix 클라이언트가 이 member 보고를 관리 승인으로 직접 제출할 수는 없다. 새 wire purpose/kind·별도 Raft/native 경로를 추가하지 않는다. 원 Plan/Operation/resource request ID와 Unknown을 보존한다. 앱 조회의 optional Replacement 진행 형식은 [Unix API](../../reference/unix-sockets/22-credential.md#rq5-순차-교체-상태)를 따른다.

이관용 `app-plan-stream`의 AppMovePlan JSON에는 선택 `StoragePreflight`가 붙는다. 기존 node-observation에서 installed target key·서명·index·시각과 현재 tenant의 ManageVolumes/Deploy를 확인한 측정만 사용한다. 형식과 상태는 [CLI 이관 계획](../../cli/volume.md#다른-서버로-옮기기)을 따른다. 원 Begin/Artifact·고정 만료·transfer/현재 quorum 권한은 그대로이며, 디스크 측정을 native Ready나 실행 승인으로 사용하지 않는다. 새로운 메시지 종류·쓰기 경로를 추가하지 않는다.


### CD 로컬 서비스 작성자 승인

`put-app-local-services`/`clear-app-local-services`는 기존 사용자 submit/result/resume를 사용한다. [Payload·CAS](../../reference/unix-sockets/11-section.md#cd-로컬-서비스-편집-메시지)를 따른다. 설치된 node key가 추가 서비스의 사용자 승인을 만들지 않는다. AppDeliverySync/BindingSource에 별도의 서명된 local grant를 고정하고 원 CD 등록/Group requester와 함께 현재 권한을 검사한다. source 후보의 편집/clear로 수락된 원 실행의 grant를 교체하지 않는다. 원 Git bytes·등록 신원·Raft 적용 순서·schema1을 유지한다.


### Replica Ingress backend 관측

내부 app-progress의 optional Observation.IngressBackends는 정렬된 exact Task Key/Generation/Revision 목록이다. 이 목록과 IngressDrained는 원 Step.Identity/Goal.Follow의 복제본만 담는다. 고정 Task는 전체 backend 관측과 Task health로 확인하며 복제본 전이 목록에 넣지 않는다. 원 Ingress owner가 기존 balancer에서 실제 준비된 backend를 보고하며 새 Task/source 자체를 만들지 않는다. FSM은 같은 accepted plan의 명시 replica identity와 current/held ref를 대조한다. next-wave와 전체 완료는 각각 필요한 새 backend 증거를 요구한다. source schema는1을 유지하고 이 목록이 없는 legacy signed 입력의 bytes를 변경하지 않는다. Goal의 optional Follow는 원 app의 replica instance 목록으로 한정하며 고정 망 source의 lifetime 및 현재 사용자/원 Binding grant를 우회하지 않는다. [관측 형식](../../reference/unix-sockets/22-credential.md#rq5-순차-교체-상태)과 [수명 설명](../../mechanisms/networking.md#replica-ingress의-listener와-backend-수명)을 따른다.


### RQ5 `begin-app` 대상 CAS

기존 plain 앱 갱신에는 `AppView.BeginTarget`을 `AppBegin.Target`에 고정할 수 있다. `Expected`는 읽은 inventory revision floor이고 `UserOperation`은 그 원 root/epoch/ID와 Target을 함께 서명한다. 유효한 Target이 있는 요청만 기존 `ModuleAppCAS` kind를 사용한다. 지문은 원 Origin/sync, Scope, down/pending 의도, 원 active operation/plan/status, retirement, task restart/log clear 의도를 포함하며 health sequence/시각과 완료 시각·독립 upload revision은 제외한다. 현재 Target 일치와 미래 좌표 거부 뒤 같은 reducer가 원 Blueprint·현재 권한/배치/quota/소스·writer/retirement를 다시 검증한다. CAS가 native 종료나 가용성을 보장하지 않는다.

`sfcli app deploy`는 기존 plain 앱의 BeginTarget을 artifact/expected/epoch와 같은 로컬 intent에 보존하며 upload 전후나 resume에서 다시 선택하지 않는다. 신규 앱은 expected=0과 cluster/tenant/app/deployment별 부재 Target을 함께 고정한다. 서버는 해당 앱 entry가 여전히 없을 때만 수락하며 다른 앱의 checkpoint로 root만 바뀐 경우 현재 Blueprint·권한·배치·quota·소스를 다시 검증한다. 부재 지문은 `SHA-256("sfc-app-create-target-1\x00" || JSON({Cluster,Tenant,App,Deployment}))`이며 필드 순서와 대소문자는 이 순서대로, Cluster는 32바이트 정수 배열이다. 기존 앱에 expected=0으로 적용할 수 없으며 CD 앱도 덮어쓸 수 없다. Target 없는 과거 intent/서명은 기존 엄격 root/inventory CAS를 유지한다. 거부/불명 뒤 새 Target·서명·ID로 자동 재제출하지 않는다.

순차 교체의 내부 signed Observation에는 optional `IngressDrained:[{Key,Generation,Revision}]`가 있다. listener owner가 해당 원 Task 세대의 신규 요청 차단과 진행 중 HTTP lease의 내구 반환을 확인한 양의 사실이며, health 목록의 부재와 다르다. 정렬·고유·원 Task ref와 서명을 검증하고 해당 원 ref가 serving 목록과 동시에 존재하면 거부한다. Inventory는 이 사실 전에는 파동 Task의 첫 Drain을 dispatch하지 않는다. 기존 listener와 그 보존 중인 producer의 exact noop 준비·관측만 retirement 중 허용하며 listener 생성/변경은 허용하지 않는다. 이미 dispatch한 원 Drain의 Unknown/proof/delete 정산은 유지한다. nil 필드는 생략해 기존 schema1 서명 bytes를 유지한다. 관리 Unix의 사용자 호출 메시지를 추가하는 계약이 아니다.

User `external-registries`는 tenant Read 또는 ManageRegistry의 공개 참조 페이지다. `put-external-registry`/`delete-external-registry`는 기존 서명된 관리 operation과 Raft/root/record CAS로 실행한다. payload와 응답·민감 값 연결 범위는 [외부 registry](../../reference/external-registries.md)를 따른다. External은 선택한 참조이며 원문 자격이나 fetch 승인이 아니다. 삭제/비활성 정의는 익명 fallback을 허용하지 않는다.

외부 registry의 보호된 앱 읽기는 registry-image-permit의 optional ExternalInputs `{ReadSet,Entries:[{Realm,Leaf,Provider}]}`로 공개 exact reference를 고정한다. 기존 SecretFetch/AppInputFetch 포맷은 유지한다. provider는 해당 leaf가 RegistrySources에만 속할 때 실제 원 Task image의 현재 registry permit까지 재검사한다. 원 승인·ReadSet·leaf/provider와 읽기 전후 권한을 검증하며, 이 보조 값은 앱 파일/env merge에서 제외한다. [외부 registry 공급](../../reference/external-registries.md#승인값-공급과-실제-연결-범위)을 따른다.

외부 source의 앱 없는 관리 읽기는 User `external-registry-bind-plan`·서명 action `bind-external-registry`로 선택 owner와 purpose=`registry-source`의 사용 참조를 예약한다. 기존 Vault 승인 target에는 optional `purpose`가 서명되며 기본 앱 승인은 빈 purpose를 유지한다. User `registry-login-test`는 원 Session과 선택을 owner의 Management `external-registry-probe`로 전달하고 현재 권한을 I/O 전후에 검사한다. source의 node 전용 `external-registry-work`·`external-registry-closed`와 SecretFetch의 optional ExternalRegistry selector는 [입력·응답 명세](../../reference/external-registries.md#앱-없는-관리-source-승인과-로그인-시험)를 따른다. Draining 뒤 실제 I/O 종료와 원 grant의 서명 증명 전에는 usage를 반환하지 않는다.

User `image-resolve`는 현재 tenant Read 또는 ManageRegistry의 `{Tenant,ImageResolve:{Ref}}`를 받고 공개 digest/index·source 분류·신뢰 결과를 반환한다. node 간 `image-resolve-owner`는 원 Session·조회 대상과 source read-set/내장 run을 그대로 전달하며 node owner가 I/O 전후 현재 허가를 재검사한다. 신뢰되지 않은 주소에는 네트워크 요청을 보내지 않는다. 별도 credential·새 전송 purpose를 만들지 않으며 [메시지·결과 코드](../../reference/image-resolution.md)를 따른다.

User `image-usages`는 현재 tenant Read 또는 ManageRegistry로 `{Tenant,ImageUsage:{Refs?,ExternalSource?},After?}`를 받고 `{ImageUsages:{Schema,Tenant,Root,Index,Rows,Next}}`를 반환한다. 허가된 참조 집합과 selector에 cursor를 고정하고 원문 없는 과거 버전을 reference 0으로 주장하지 않는다. [사용처 메시지](../../reference/image-usages.md)를 따른다.

node 전용 registry-image-permit의 선택 ConfigID는 실제 준비/재생성할 native image ID(legacy config digest 또는 containerd의 검증된 manifest digest)의 캐시 admission fence를 확인한다. 원 named image·Task/Binding·현재 신뢰/자격 검사를 대체하거나 configID를 origin 증거로 취급하지 않는다. 빈 ConfigID의 기존 schema1 메시지는 유지한다. 이 필드는 Unix User method의 일반 이미지 조회 입력이 아니다.

User `external-registry-pulls`는 `{Tenant,After?}`로 현재 Read 또는 ManageRegistry의 코드 전용 실제 받기 관측을 읽는다. `Reply.RegistryPulls:{Schema,Tenant,Root,Index,Rows,Next}`는 [실제 pull 형식](../../reference/external-registries.md#실제-이미지-받기-결과-조회)을 따른다. 기존 서명 `node-observation` Report의 optional `RegistryPull:{Tenant,Authority,Source,Stage,Code,CompletedAt,Sequence}`로 전달하며 원격 body/자격을 넣지 않는다. envelope At는 재보고 시각이고 CompletedAt는 실제 완료 시각이다. source/app grant나 실행 허가를 만들지 않는다.

User `registry-catalog`는 `{Tenant,RegistryCatalog:{Kind,ID,Repository?},After?}`로 현재 Read/ManageRegistry의 공개 목록을 읽으며 `Reply.RegistryCatalog:{Kind,ID,Page}`의 [8행 페이지](../../reference/registry-images.md)를 반환한다. 내부 owner 연결은 원 사용자 Session·고정 source/run·read-set을 담은 Management `registry-catalog-owner`를 사용한다. owner가 현재 권한을 I/O 전후에 재검사하고 실제 serving Store 또는 승인 external reader를 사용한다. 내장 시각 fact는 owner DB에만 두며 Raft에 image body/목록을 복제하지 않는다.

User `registry-maintenance-plan/status`와 signed action `delete-registry-image/gc-registry`는 [삭제·GC 메시지](../../reference/registry-maintenance.md)를 따른다. 원 run·사용자 grant·target CAS를 `control/registry-maintenance` job에 고정하며 root revision은 `whoami`와 `registries`의 RegistryMaintenanceRootRevision으로 읽는다. owner 전용 latest-quorum Management `registry-maintenance-work` 입력은 `{Operation,At,Images?}`(Images 최대32개), 응답은 `{Schema,Cluster,Owner,Operation,Action,State,Revision,RootRevision,Epoch,Index,Change,Allowed,InUse}`다. 실제 native 효과 직전 같은 current authority/참조를 검사한다.

Management `registry-maintenance-report`는 `{Schema:1,Cluster,Owner,Operation,Action,Expected,RootRevision,Epoch,At,Result?,Signature}`다. Action은 begin·complete 또는 외부 작업의 uncertain, Expected는 원 job row CAS, At은 Unix 초다. begin/uncertain에는 Result가 없고 complete에는 제한된 RegistryMaintenanceResult가 필수다. uncertain은 외부 전송의 결과 불명을 unknown 상태로 보존하며 새 native 효과를 허가하지 않는다. unknown에서 complete하려면 확인된 원 응답/receipt의 Native 지문이 필요하고 권한 상실만으로 DENIED 정산하지 않는다. 원 installed owner가 `sfc-registry-maintenance-report-1\x00` domain 뒤 Signature를 nil로 직렬화한 JSON에 Ed25519로 서명한다. 동일 공유 reducer가 pending admission fence와 원 결과를 갱신한다. 이 node 메시지는 사용자 관리 동작을 새로 발급하지 않으며 저장된 원 native intent의 양성 cleanup도 같은 ID로 정산한다.

User `registry-prune-preview/results`·signed `prune-registry-images`는 [일괄 정리 명세](../../reference/registry-maintenance.md#일괄-정리)를 따른다. 내부 Management `registry-prune-owner` 입력은 `{Read:{Session,Tenant,Query,After,Base},Results}`이고 응답은 RegistryPruneView다. installed member의 전달과 원 사용자 현재 권한을 모두 검사한다. 서명 Fact의 target/조건/preview/Public 지문을 고정하고 같은 maintenance parent와 item receipt/선택 GC를 사용한다. 큰 목록·별칭 배열·이미지 body를 Raft에 복제하지 않는다. 외부 단회 전송 불명은 부모 unknown이며 새 항목 전송을 중단한다.


### ImageContent — purpose16

kind16은 설치된 builder member가 수락된 원 job의 FROM graph 본문을 원 source owner에서 읽는 QUIC 전용 실행 요청이다. Body/원 accepted read·Root/Path·현재 권한/reader 검사와 형식은 [수락 빌드 본문](../../reference/image-content.md#수락된-빌드의-from-본문)을 따른다. Session/사용자 Signature/Relay가 없는 `{Body}`를 사용하며 연결 member key가 원 Builder여야 한다. 원 고정 root와 모든 index edge를 확인하고 같은 kind2/4·길이/지문·최종 EOF 계약으로 전달한다. node CLI 권한이나 새 사용자 명령을 발급하는 경로가 아니다. 자체 schema 번호와 기존 kind1–4 형식은 유지한다.

원 이미지 manifest·config/history·layer 읽기는 [ImageContent](../../reference/image-content.md)를 따른다. Unix TLS와 QUIC에 같은 read-only handler·원 사용자 proof·trust/source/run 검사를 적용한다. kind1/3 요청의 Body는 ImageContentRequest, kind2는 ready/최종 ok 또는 제한된 거부이고, kind4는 연속 offset의 원 바이트다. 임의 blob/URL을 받지 않고 immutable manifest의 descriptor에 묶는다. 최대 layer10GiB를24KiB frame·일정 메모리로 흐르게 하며 실제 전체 길이/지문·최종 ok/EOF 전까지 소비자가 공개 cache로 확정하지 않는다.

노드 간 relay는 설치 member의 kind3이며 User grant/원 Body와 사용자 proof를 바꾸지 않는다. 응답은 각 연결의 원 Envelope digest·request ID에 연결한다. Unix는 kind3을 받지 않는다. 전용 local 연결은 종료 뒤 cache에서 반환하고, 파싱30초/계획5초 뒤 원 만료(max900초)·I/O 유휴60초와 node별 handler2개를 적용한다. 일반 User RPC의30초 제한과 기존 목적 번호·schema1은 유지한다. 원 권한/승인은 전송 중과 마지막 결과에 다시 검사하며 연결·SDK body의 실제 종료를 원 reader 사용 참조 반환과 연결한다.


### 원 빌드 게시의 owner 관측

member Management `image-build-publication-owner`는 원 builder가 원 registry owner에 직접
보내는 조회다. `Latest=false`, `Key`·`Command` 없음으로 native owner에 남고, owner가
별도로 quorum을 읽어 scope를 확인한다. User purpose8/Unix 사용자 명령이 아니다.

입력은 `{Tenant,Job,Snapshot:[32],Target}`이다. Snapshot은 수락된 JobSpec.Digest이고
Target은 그 job의 정확한 OutputTags 중 하나다. 설치된 원 builder key·tenant/job·snapshot·
현재 원 registry spec/data namespace를 검사한다. queued job·다른 노드/태그/tenant는 거부한다.

응답은 `{Schema:1,Read:{Query,Run,Index,Epoch},Code,Result?}`다. Run은 기존 RegistryRunRef,
Code는 OK/NOT_FOUND/UNAVAILABLE다. OK의 Result는 기존 registryclient.Resolution
`{Normalized,Registry,Repository,Pinned,Digest,MediaType,ManifestBytes,Platforms?}`이며
다른 Code에는 없다. image/manifest/config 본문·Secret·로그인 토큰을 반환하지 않는다.
owner와 caller는 I/O 전후·응답 index 이후의 현재 원 run을 재검사하고, readiness heartbeat와
같은 run의 drain은 read identity 변경으로 취급하지 않는다. 다른 run/Volume namespace는 거부한다.

원 job의 만료·취소·관리자 권한 회수 후에도 원 태그 관측은 새 push 허가와 분리한다.
이미 전송한 root의 일치 관측만 정산 근거이며 NOT_FOUND·단절·다른 digest는 미실행이나
재전송 허가가 아니다. 미종결 running/unknown 빌드가 같은 원 registry를 사용하면 listener를
닫아도 원 Store/pin은 정산용으로 유지하며, 모든 원 빌드 종결 전 closed/Volume 반환을 막는다.
재시작은 원 recorded lease와 KnownData DB가 있는 경우에만 Store를 다시 열며 새 lease·빈
DB·listener를 만들지 않는다. [게시·정산 경계](../../reference/image-build-jobs/09-registry.md)를 따른다.

빌드의 유한 native daemon은 job-private Unix gRPC socket에서 고정 BuildKit SDK만 상대한다. 이 연결은 노드 간 SFCP를 우회하는 TCP/RPC가 아니며 원 context/출력 FD·source policy·Secret/auth session에 한정한다. 노드 간 source token은 위 SFCP 메시지를 유지한다. SDK solve 결과와 native Stop/Wait/Remove의 구분은 [job 실행 수명](../../reference/image-build-jobs/07-section.md)을 따른다.

member image-build-base-tls-owner는 원 BaseRead, image-build-registry-tls-owner는 원 RegistryPermit을 받아 `{Authority,Certificates:[DER base64],Fingerprint}`를 원 Builder에게 반환한다. 새 transport/wire 번호나 사용자 Vault API를 만들지 않으며 [공개 TLS 자료·예산·원 scope](../../reference/image-build-jobs/06-tls.md)의 current quorum/reader/registry serving leaf를 검사한다. private key/password·OS/Engine trust 변경은 포함하지 않는다.

검증한다. [형식·CacheScope·cursor 호환](../../reference/image-build-jobs/13-cache-id.md)을 따른다.
새 purpose/소켓을 추가하거나 사용자 조회를 cache 삭제로 바꾸지 않는다.

기한은 이번 pass At와 현재 수락 정책 Seconds로 계산하며 원 Source Spec은 그대로 보존한다.

기존 member `tenant-retirement-work/report`는 [폐기 가능한 build cache의 물리 정산](../../reference/image-build-jobs/17-tenant.md)에도

반환이 끝난 뒤에만 owner의 최종 종료 보고를 수락한다. Volume/backup 삭제는 기존 명시 작업이다.

오류/Description을 응답에 추가하지 않는다.

User purpose8의 보존 `build-context-content Part:file`와 mutable `build-draft Kind:file`는 [regular file 페이지](../../reference/image-build-contexts/04-dockerfile.md#임의-regular-file의-페이지와-eof-확인)를 사용한다. 보존 파일은 원 Version/Tree/Path와64-bit Offset/cursor, draft는 원 Scope/Revision/Digest/Path와 byte Offset에 고정한다. 한 페이지의 Data는24KiB이며 전체 크기/지문/실행 bit를 원 tree Entry로 반환한다. Unix/QUIC의 인증·EOF·현재 권한·member owner relay는 동일하다. 새 file 종류의 owner 응답은 허용 Code와 요청에 맞는 Content 또는 Draft만 담고 native 오류 문자열을 반환하지 않는다. Read-only는 보존 version을 읽을 수 있으나 mutable draft는 읽지 못한다.
