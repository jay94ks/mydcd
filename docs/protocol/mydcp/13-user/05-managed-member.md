### managed 앱 member 실행 경계

User의 `app-plan`은 optional Diff=true일 때 같은 Compile과 Inventory.Changes로 schema1 AppDiff를 반환한다. Tenant/App/Deployment·원 plan digest·Apps root/inventory revision·Changes를 전체 digest에 결합하며 기존 AppPlanPart의24KiB paging을 사용한다. 입력/응답 한도·현재 Deploy/각 단계 권한·정책 변경 시 conflict는 plan과 같다. 관리 상태를 변경하거나 native 효과를 제출하지 않는다. Diff가 없으면 기존 Blueprint 응답이다.

User의 `app-plan-stream`은 AppPlan.Document=null/Part=0과 AppInput.Length/Digest를 원 Body 서명에 결합한다. 길이는1..4MiB다. 현재 session/Deploy를 검사한 kind2 Code=continue 뒤 같은 request의 kind4를 정확한 offset/조각 길이로 받고 전체 digest/EOF를 검증한다. 전송 후 최신 quorum/current issuer·사용자/단계별 권한을 다시 검사하고 기존 AppPlanArtifact/Compile/Inventory.Changes로 한 snapshot을 계산한다. kind2 Code=ok의 AppPlanPart들을 같은 stream에 순서대로 보내며 client는 전체 길이/part/digest·원 request/header digest·Node/RelayedBy 일치와 최종 EOF를 검사한다. 입력/출력은 각각4MiB·기존 User 동시성16/stream deadline30초의 경계를 사용하며 임시 DB 후보/내구 ACK·관리 효과는 만들지 않는다. continue는 전송 허가이고 배포 수락이 아니다.

follower는 bounded 입력 검증 뒤 현재 leader에 기존 kind3 relay1회로 원 Body/Session/사용자 proof를 전달한다. 원 입력 digest와 새 대상/연결의 relay 서명을 함께 대조한다. leader는 입력 전/후 committed view의 relay member 자격과 최신 quorum/사용자 권한·같은 입력을 재검증하고 follower는 검증한 결과만 원 연결의 header digest에 결합해 반환한다. kind3을 다시 relay하지 않는다. 단절/변조/미완성 전송은 결과/부분 파일을 게시하지 않으며 새 배포 operation을 만들지 않는다. 기존 단일 frame app-plan의24KiB 입력과 독립 요청 paging은 유지한다.

User의 `apps`는 현재 quorum view에서 Health/ObservedAt/ObservationMaxAge를 추가한다. 시간은 adapter가 주입하며 FSM에 현재 시계를 넣지 않는다. 동일 원 owner/command/generation/revision에 결합된 저장 관측이 만료 표시(`Expired`) 없이 살아 있는지를 기존 Execution.Health로 판정한다. 소유자는 사실이 그대로면 15초마다 `app-observation-renew`로 리더에게만 갱신을 보내고 Raft에는 쓰지 않는다. 리더는 30초 동안 갱신·새 사실이 없으면 `expire-observation` 보고를 한 번 Raft에 남긴다. `ObservedAt`은 마지막으로 바뀐 사실의 시각이다. retirement와 실행 부재는 Unknown이다. Succeeded는 과거 완료 사실이며 현재 Healthy를 보장하지 않는다. CLI의 wait는 이 읽기 계약만 소비한다.

선택 bool `AppView.ImageSourceNoLongerTrusted`는 현재 tenant repository trust와 accepted 실행/미제거 Task claim의 출처를 비교한다. 현재 health·원 작업 결과·native 종료와 별개다. false는 생략해 schema1의 기존 응답을 유지한다. 페이지 소비자는 AppsRootRevision과 기존 Reply.RootRevision(Catalog root)을 함께 고정하며 CLI 목록은 CatalogRootRevision도 표시한다. 새 권한·별도 동기화 상태를 만들지 않는다.

User method `app-operation`은 Request.AppOperation의 App/ID와 Tenant를 원 envelope 서명에 결합한다. 다른 method의 AppOperation 혼입·nil selector·After를 거부한다. 기존 latest quorum/current session/tenant Read·member relay1회 경로를 사용하며 Apps.Inventory.Operation만 읽는다. Reply.AppOperation은 Tenant/App/Deployment/ID·inventory Revision·Found/Current와 선택 원 OperationSummary를 포함한다. AppsRootRevision은 같은 committed root다. 원 Plan/submitter/epoch/실패·종료 결과를 반환하고 현재 health/native 생존을 단정하지 않는다. Found=false는 미실행 증거가 아니며 client의 새 제출을 허가하지 않는다. 별도 이력 저장소·Raft 명령·purpose·schema 번호를 추가하지 않는다.

기존 서명된 Management envelope의 kind3/Latest=true로 다음 method를 전달한다. 즉시 원격 인증된 current member/Read 권한을 검사하고, leader의 최신 quorum view에서 원 caller를 다시 검사한다. follower는 기존 kind4의1회 member relay만 사용한다. user session/tenant manager 권한은 이 member 권한을 대신하지 않으며 `Key`/별도 `Command` 필드는 비워야 한다.

- `app-progress`: Input은 schema1 AppProgress다. Reporter와 원 caller가 같고 현재 member여야 한다. 원 cluster/operation/key·inventory/root CAS·epoch·시각·서명을 검증하고 기존 Inventory/Execution으로 Prepare/Send/Unknown/Collect/Observe/Finish를 적용한다. 새 보고는 미래 시각/300초 초과를 거부하며 보존된 정확한 원 결과는 다시 조회할 수 있다. Applied ACK와 실제 native 완료는 구분한다.
- `app-observation-renew`: Input은 Action=`observe`인 schema1 AppProgress다. 리더만 받는다. 저장된 관측과 사실이 같고(순번·시각·서명만 새로움) 만료 표시가 없을 때만 받아 리더 메모리에 마지막 갱신 시각을 둔다. Raft에 쓰지 않으며 응답은 빈 객체다. 사실이 바뀌었거나 만료된 관측은 `app-progress`의 observe로 보낸다.
- `app-progress`의 `expire-observation`: Key와 ExpireSequence(만료할 저장 관측의 순번)를 담는다. 리더가 그 관측의 마지막 갱신(메모리, 저장 시각, 리더가 된 시각 중 가장 늦은 것)이 30초를 넘으면 보낸다. reducer는 순번이 같고 저장 시각이 30초를 넘었을 때만 `Expired`를 표시한다. 앱 관측 JSON의 `Expired`(생략 시 false)는 이 표시다. 서명 bytes에서 빠지며 노드가 보낸 관측에 있으면 거부한다. 아직은 어느 member 키든 이 보고를 보낼 수 있고 reducer는 보고의 At을 현재 시각으로 쓴다. 지금은 리더만 보낸다.
- `app-command`: Input은 frozen 원 state.Command의 인코딩이다. 현재 accepted grant/계정/credential/role/node/trust와 정확한 Dispatched/RecoveryRequired stage를 검사한 뒤 같은 A1에 제안한다. actor/ID/epoch/CAS/Goal bytes를 caller가 바꿀 수 없다. 보고자가 새 결과를 공급하지 않으며 원 중복 결과를 보존한다.

`app-progress`와 `volume-backup-report / volume-restore-report / volume-delete-report / volume-create-report`의 새 A1 제안은 schema1 명령 종류 `ModuleReport`를 사용한다. 원 payload/서명을 유지하고 바깥 ID는 전체 command의 내용과 root CAS에 결합한다. 확정 checkpoint에 반영된 보고의 영수증 수명은 보고 수명 계약을 따른다. 최신 원 결과와 일반 사용자/native 명령 결과는 보존하고, 회수된 보고의 부재/만료를 미실행이나 새 효과 재제출 권한으로 해석하지 않는다. 기존 schema1 Module 보고의 정확한 영수증이 남아 있으면 같은 payload 재전송은 그 원 ID/결과를 사용한다. 새 MYDCP 목적이나 별도 RPC 경로는 만들지 않는다.
- `app-result`: Input은 원 stage/claim에 묶인 정확한 Command다. 실제 A1 receipt 또는 이미 정산한 그 stage/claim result만 Found=true로 보낸다. Found=false는 미실행 증거가 아니며 자동 재제출을 허가하지 않는다.
- `app-native-permit`: Input은 AppNativeRequest.Source의 key/generation/revision이다. 현재 app/source/owner·확정된 원 Applied 결과·현재 수락 grant/권한·global/tenant 양수 consumer 한도를 검사한다. 응답 AppNativePermit은 Source/Owner/Kind/정규 native 재료의 SHA256/MaxConsumers를 담는다. Bridge는 lifecycle을 제외한 BridgeSpec, Volume은 원 NativeSpec/물리 Generation을 담은 AppVolumeMaterial의 정규 JSON을 해시한다. owner는 신규 실행 직전에 조회/대조한다. 보관된 ticket이나 분리된 권위 저장소를 만들지 않는다.
- `app-binding-permit`: Input은 AppBindingRequest의 원 Task key/generation/revision·Binding digest·At다. owner와 현재 member가 같아야 하고 Latest quorum view에서 원 Task/inputs·수락 scope와 현재 권한·Secret 승인/원 usage·Volume consumer·현재 node 예산을 검사한다. At는 미래/30초 초과를 거부한다. 응답은 원 Task/inputs·공개 Binding 바이트·MaxConsumers·공개 read-set digest/CommandIndex이며 값/비밀번호/host path를 포함하지 않는다. reader는 그 최소 command index 이상인 로컬 확정 상태에서 같은 Binding/read-set을 대조한다. 실제 fetch 뒤 최신 허가를 다시 확인하고 projection 게시/새 취득도 현재 gate를 통과해야 한다. 허가는 새 읽기/주입/활성을 위한 것이고 원 종료 정산과 구분한다.

AppProgress는 추가 action `bind-inputs`/`release-inputs`를 제공한다. Key는 원 Task이며 예약의 Needs/consumer는 caller에게 받지 않고 확정 Execution에서 도출한다. Task와 해당 inputs의 실제 Applied 결과/원 세대가 필요하다. 반환은 optional Release의 Binding digest/모든 Secret·Volume 종료 proof와 원 owner가 서명한 Task 종료 Observation을 함께 받는다. 추가 필드가 없는 기존 signed AppProgress 바이트는 유지한다. 실제 native 효과 완료를 metadata 예약으로 추정하지 않는다.

`volume-ready` action은 원 Volume Goal의 Key와 optional Volume의 서명 NativeReady, 같은 native 이름/원 command의 owner Observation을 함께 전달한다. fresh owner 허가·원 spec/물리 generation·서명을 확인하고 Execution/Inventory 관측과 최초 shared Volume 등록을 같은 FSM 변경으로 게시한다. 관련 namespace 허가는 control/volumes 하위로만 한정한다. 이미 등록된 원 준비 사실은 교체하지 않는다. nil Volume 필드는 생략해 기존 보고의 서명 바이트를 유지한다.

앱 종료는 user의 typed `down-app` 변경(AppDown: Tenant/App/Operation)과 원 inventory CAS로 수락한다. 원 signed cleanup grant를 app checkpoint에 보존하고 실제 권한/credential과 원 scope를 계속 검사한다. node 배치 회수는 기존 자원 cleanup의 권한 검사를 신규 배치 검사로 바꾸지 않는다. 조회의 optional Retirement는 종료 ID와 Retiring/Retired를 구분하며 수락 자체를 종료 완료로 보고하지 않는다.

종료 진행은 같은 `app-progress`의 `retire-send / retire-unknown / retire-collect / retire-gone / retire-retain / retire-finish` action과 optional Retire payload를 사용한다. Operation은 retirement ID다. send/unknown/collect는 Phase=drain/proof/delete, gone은 원 Drain에 대한 owner 서명, retain은 원 RetainReceipt만 허용한다. Inventory가 만든 원 command/epoch/actor/ID/CAS와 내구 result만 `app-command / app-result`에 결합한다. 원 명령이 Dispatched인 경우 결과를 관측할 뿐 새 ID/재전송을 만들지 않는다. Task/inputs의 공유 Binding이 남아 있으면 종료 proof 게시를 거부하고 전체 Binding 반환 이후 원 proof/delete를 진행한다. namespace 추가 허가는 발생하지 않는다. nil Retire는 생략하여 기존 보고 서명 바이트를 유지한다.

단절/무과반수는 새 실행 허가를 주지 않는다. 기존 native journal의 원 dispatch 복구·종료·결과/관측 정산은 새로운 생성 허가와 구분한다. 독립 owner의 Bridge/Task·Vault/Volume·앱 실행은 이 permit과 원 Binding/journal을 사용한다. 리더 인계가 native owner나 이미 전송한 작업의 ID를 바꾸지 않는다.
