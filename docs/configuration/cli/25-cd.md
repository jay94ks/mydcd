## 교체 미리보기와 진행

CD 명령은 [sfcli cd](../../cli/cd.md)에 있다.

`compose diff`의 optional `Replacement`는 다중 노드 배치의 교체 영향 미리보기다. 원 Task key와 원 세대/리비전, 노드별 종료 대상을 확인할 수 있다. `BlockedCode`가 있으면 Waves는 비며 의존성 충돌 또는 원 미정산 작업을 먼저 해결해야 한다. 이 조회가 컨테이너를 멈추거나 순차 갱신을 시작하지는 않는다. [원 메시지 형식](../../reference/unix-sockets.md)을 따른다.

RQ5 앱 조회의 `Replacement` 진행 정보는 1부터의 Wave/Waves·Node·Phase를 나타낸다. 원 배포/CD operation을 그대로 조회하며 파동마다 up/sync를 새로 제출하지 않는다. Phase complete도 원 Operation의 최종 성공과 구분한다. 신선한 첫 노드 health가 없거나 원 결과가 Unknown이면 후속 노드를 변경하지 않는다.


### RQ5 `begin-app` 대상 CAS

기존 plain 앱 갱신에는 `AppView.BeginTarget`을 `AppBegin.Target`에 고정할 수 있다. `Expected`는 읽은 inventory revision floor이고 `UserOperation`은 그 원 root/epoch/ID와 Target을 함께 서명한다. 유효한 Target이 있는 요청만 기존 `ModuleAppCAS` kind를 사용한다. 지문은 원 Origin/sync, Scope, down/pending 의도, 원 active operation/plan/status, retirement, task restart/log clear 의도를 포함하며 health sequence/시각과 완료 시각·독립 upload revision은 제외한다. 현재 Target 일치와 미래 좌표 거부 뒤 같은 reducer가 원 Blueprint·현재 권한/배치/quota/소스·writer/retirement를 다시 검증한다. CAS가 native 종료나 가용성을 보장하지 않는다.

`sfcli app deploy`는 기존 plain 앱의 BeginTarget을 artifact/expected/epoch와 같은 로컬 intent에 보존하며 upload 전후나 resume에서 다시 선택하지 않는다. 신규 앱은 expected=0과 cluster/tenant/app/deployment별 부재 Target을 함께 고정한다. 서버는 해당 앱 entry가 여전히 없을 때만 수락하며 다른 앱의 checkpoint로 root만 바뀐 경우 현재 Blueprint·권한·배치·quota·소스를 다시 검증한다. 부재 지문은 `SHA-256("sfc-app-create-target-1\x00" || JSON({Cluster,Tenant,App,Deployment}))`이며 필드 순서와 대소문자는 이 순서대로, Cluster는 32바이트 정수 배열이다. 기존 앱에 expected=0으로 적용할 수 없으며 CD 앱도 덮어쓸 수 없다. Target 없는 과거 intent/서명은 기존 엄격 root/inventory CAS를 유지한다. 거부/불명 뒤 새 Target·서명·ID로 자동 재제출하지 않는다.

registry·이미지·빌드 명령은 [sfcli registry](../../cli/registry.md)·[sfcli image](../../cli/image.md)·[sfcli build](../../cli/build.md)에 있다.

빌드의 외부 tenant CA와 내장 registry serving chain은 원 source/registry owner에서 공개 인증서만 가져온다. CLI에서 OS/Docker CA를 설치하거나 Vault의 registry password/key 파일을 빌더에 복사하지 않는다. 원 job에 고정한 private daemon 설정·호출별 HTTPS client와 [TLS 신뢰 계약](../../reference/image-build-jobs/06-tls.md)을 따른다.

일반 build job/context/policy 삭제는 재사용 cache namespace를 보존한다. 기존 관리 명령으로
tenant 종료를 시작한 경우에는 [원 owner의 물리 cache 정산](../../reference/image-build-jobs/17-tenant.md)이
마지막 종료 점검에 포함된다. cache 반환만을 위한 새 사용자 로그인/명령이나 CLI 상시 실행은
없으며, 미정산 lease가 있으면 tenant 종료 상태가 완료로 바뀌지 않는다.


캐시 목록/항목 응답의 ObservedKind가 `cache-prune`이면 ObservedBy는 원 수동 정리
intent다. 생략은 기존 build Spec digest다. Prune 뒤 재관측 실패는 이전 성공과
UNAVAILABLE을 함께 표시하며 정리 결과 자체와 구분한다. [관측 출처](../../reference/image-build-jobs/14-section.md#수동-정리-관측과-조회의-출처)를 따른다.
