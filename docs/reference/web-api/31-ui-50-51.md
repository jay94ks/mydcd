## 망 변경·폐기 (UI-50·51)

데몬이 망의 멤버 행(`resources`의 tenancy.Network와 change 상태)에서 payload를 만든다. 응답은 `{op}`, `opId` 규칙은 공유 자원 만들기와 같다. 권한과 순서 판단은 mydcd가 한다(TM(Network)). 한 멤버는 계획(reserved) → 비우기(draining) → 막기(fenced) → 확정 순서로 가고, 계획만 된 것(reserved)은 취소할 수 있다.

막기(fence)와 bridge 망 폐기는 소유 서버가 서명한 closure를 넣는다. 데몬이 `PublicRead` `network-closure`로 읽는다. 비운 멤버를 아직 쓰는 컨테이너가 있으면 409 `in-use`이고, 서버가 응답하지 않으면 409 `unreachable`이다. 화면은 `closure`의 `pendingEndpoints`로 "남은 사용 N 컨테이너"를 보여 준다(어느 컨테이너인지는 `…/users`). 망을 쓰는 앱 전체 목록은 `GET /t/{t}/networks/{name}/users`(REQ-35, `network-users`)에서 오고, 응답 모양은 저장소의 `…/users`와 같다.

망 행(`GET /t/{t}/networks`, `resources`)에는 `members:[{node, id, cidr, tunnel?, generation, revision, draining, change?:{id, generation, revision, targetRevision, phase, targetCidr, metadataOnly?}}]`가 붙는다.

| 끝점 | 본문 → action |
|---|---|
| `GET /t/{t}/networks/{name}/change` | `{name, kind, networksRevision, dnsEnabled, members:[{node, id, cidr, tunnel?, revision, draining, phase(none/reserved/draining/fenced), target, change?}], next(drain/fence/commit/""), closure:[{node, state(pending/unreachable/closed), closed, unreachable, nativeGone, pendingEndpoints, pendingFlows, pendingPins}]}`. mydcd가 재지 않은 수와 nativeGone은 `null`이다(0으로 짐작하지 않음). 예전의 남은 컨테이너 목록 `endpoints`는 mydcd가 주지 않아 빠졌다. 확정·취소된 change는 phase `none`이다. `closure`는 비운(draining) 멤버마다 하나씩 온다 |
| `POST …/change` | `{opId, node, cidr, gateway?}` → 그 멤버의 `plan-network-change`. change ID는 `"chg-" + opId`, Expected는 멤버 `revision`. 주소 묶음 `main`의 MTU·IPAM은 그대로 둔다. 이미 진행 중이면 409 `change-pending`, 멤버가 아니면 422 |
| `POST …/change/drain` | `{opId, node}` → 그 멤버의 `drain-network`. 새 사용을 막고, 계획된 change를 draining으로 만든다 |
| `POST …/change/cancel` | `{opId, node}` → `cancel-network-change`. reserved일 때만 된다(아니면 409 `not-reserved`). 비운 뒤에는 취소가 없다 |
| `POST …/change/fence` | `{opId, node}` → `fence-network-change`. 소유 서버 closure를 넣고, Expected는 change revision이다. draining이 아니면 409 `not-draining`. 아직 쓰면 409 `in-use`(메시지에 수), 서버가 응답하지 않으면 409 `unreachable` |
| `POST …/change/commit` | `{opId, expected?}` → `commit-network-change`. 모든 멤버의 change 버전을 넣는다. tun 망만 된다(bridge는 409 `not-tun`). 멤버 하나라도 fenced가 아니면 409 `not-fenced`. `expected`를 비우면 데몬이 지금 `networksRevision`을 넣는다 |
| `POST /t/{t}/networks/{name}/reconfigure` | `{opId, members:[{node, cidr?, gateway?, tunnel?}], tunnelCidr?, expected?}` → `reconfigure-tun-network`(참여 서버 목록 전체). 모든 서버가 잠시 끊기므로, 서버만 더하거나 뺄 때는 아래 `members`·`members/leave`를 쓴다. 남는 서버는 주소 묶음과 터널 주소를 그대로 쓴다. 새 서버는 cidr와 tunnel이 필요하다(또는 tunnelCidr로 나눠 줌). 모든 지금 멤버가 fenced여야 한다. 망 옵션(toggles)은 그대로 이어지며, 켜진 옵션이 새 서버 수를 허용하지 않으면 409 `toggle-not-allowed`(먼저 끈다) |
| `POST /t/{t}/networks/{name}/members` | `{opId, node, cidr, gateway?, tunnel, expected?}` → `join-tun-network`(서버 하나 붙이기). 지금 망의 MTU를 쓴다. 다른 서버는 장치가 그대로이고 경로만 바뀐다. 이미 멤버면 409 `already-member`, 어느 멤버가 비우는 중이거나 변경 중이면 409 `member-changing`, 대역·터널 주소가 다른 서버와 겹치면 422. `expected`를 비우면 데몬이 지금 `networksRevision`을 넣는다 |
| `POST /t/{t}/networks/{name}/members/leave` | `{opId, node}` → `leave-tun-network`(서버 하나 떼기). 먼저 `…/change/drain`으로 비워야 한다(아니면 409 `not-drained`). 서버 closure를 넣고 Expected는 멤버 revision이다(409 `in-use`·`unreachable`). 마지막 서버가 빠지면 망이 지워진다(DNS를 먼저 꺼야 함, 아니면 409 `dns-enabled`). 계획한 변경 없이 망을 지우는 길이다. 남는 서버는 경로만 바뀐다 |
| `POST /t/{t}/networks/{name}/toggles` | `{opId, toggle, on, expected?}` → `set-network-toggle`(망 옵션 하나 켜기·끄기). 서버에서 끊기는 것은 없다. 모르는 옵션은 422, 지금 값과 같으면 409 `same-value`, 서버 수가 허락하지 않으면 409 `toggle-not-allowed`(`local`은 서버 하나일 때만 켠다), 어느 서버가 비우는 중이거나 변경 중이면 409 `member-changing`. 켜진 옵션 목록은 망 행의 `toggles`(없으면 빠짐)다. `local`이 켜진 망에 `members`를 보내면 409 `toggle-not-allowed` |
| `POST /t/{t}/networks/{name}/retire` | `{opId, expected?}`. tun 망은 멤버 없는 `reconfigure-tun-network`이고, 모든 멤버 fenced와 DNS 꺼짐(아니면 409 `dns-enabled`)이 필요하다. 서버를 하나씩 `members/leave`로 빼도 망이 지워진다 |

서버 하나의 bridge 망(`create-network`)은 없다. 서버 하나의 망도 멤버 하나인 tun 망이다.
