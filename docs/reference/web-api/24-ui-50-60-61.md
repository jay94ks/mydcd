## 공유 자원 만들기 (UI-50·60·61, 비밀값 보관함)

작업 공간(`{t}`)의 공유 자원을 만든다. 브라우저는 쉬운 칸만 보내고, 데몬이 mydcd의 실제 페이로드를 만들어 제품 입력 검사(`control.InputChange`)를 거친 뒤 `/ops`와 같은 길(서명 → 저장 → 보내기)로 보낸다. 응답은 `{op}`(`/ops`와 같은 모양, 결과는 `/ops/{id}`·`result`·`resume`). 권한은 mydcd가 정한다(TM(Network)·TM(Volumes)·보관함 관리). 권한이 없으면 op가 `failed`(결과 코드 forbidden)다. 칸이 틀리면 서명 전에 422 `invalid`이고 아무것도 저장하지 않는다.

같은 `opId`에 같은 본문은 저장된 op를 그대로 돌려준다(목록 revision이 그사이 바뀌어도 다시 보내지 않는다). 다른 본문이면 409 `op-conflict`.

| 끝점 | 본문 → action |
|---|---|
| `POST /t/{t}/networks` | `{opId, kind?:"bridge", name, node, cidr("10.40.0.0/24", IPv4, /29까지), gateway?(기본 첫 주소), mtu?(기본 1500, 1280~9000)}` → `create-network`(서버 하나의 bridge 망, 주소 묶음 `main` 하나). Expected는 망 목록 revision(`NetworkRevision`) |
| | `{opId, kind:"tun", name, members:[{node, cidr, gateway?, tunnel?}](1~32개, 서버마다 하나), tunnelCidr?, mtu?, toggles?:{NAME: bool}}` → `create-tun-network`(서버 간 가상망). `toggles`는 망 옵션(`local`: 서버 한 대에만 두기, 서버가 하나일 때만 true)이고 모르는 이름이나 서버 수에 맞지 않는 값은 422다. 서버마다 자기 주소 묶음 `main`과 **터널 주소**(모든 묶음 밖의 IPv4 /32)가 있다. `members[].tunnel`로 직접 주거나, `tunnelCidr`("10.255.40.0/24", /30까지)만 주면 데몬이 순서대로 .1, .2 …를 나눠 준다. 둘 다 없으면 422. 묶음끼리 겹치거나 터널 주소가 묶음 안에 있으면 422. 서버 소유 키와 게이트웨이 방식은 mydcd가 채운다. Expected는 망 목록 revision |
| `POST /t/{t}/networks/{name}/dns` | `{opId, zone("shop.internal"), upstreams?:["1.1.1.1", "9.9.9.9:5353"](4개까지, 포트 기본 53), ttl?(기본 30, 3600까지), negativeTtl?(기본 5, ttl 이하), reverse?, enabled?(기본 true), expected?}` → `configure-network-dns`(정책 전체 바꾸기). **mydcd의 망 DNS는 tun 망에만 붙는다**(bridge 망이면 op가 `failed`). 서버 하나에 도메인이 필요하면 member 하나짜리 tun 망으로 만든다. `expected`는 망 행의 `network.dns.revision`(처음은 0). 데몬은 망 행의 지금 정책에서 시작해 본문에 온 칸만 바꾼다. 본문에서 뺀 `upstreams`·`ttl`·`negativeTtl`·`reverse`와 화면이 다루지 않는 칸(client zone, 전송, 한도)은 그대로 남는다. 처음 정할 때 한도는 웹 기본값(64·512·64, 응답 4096바이트, 5초)이다. **mydcd에는 지금 정책을 읽는 사용자 method가 아직 없다**. 그 전에는 실제 mydcd에서 망 행에 `dns`가 오지 않으니 화면이 모든 칸을 보내야 한다. 칸 일부만 보내면(예: 끄기만) 나머지 칸은 데몬이 지금 값을 모르므로 웹 기본값으로 정책 전체가 바뀐다. 만들기와 DNS는 작업 두 개다(화면은 만들기가 applied된 뒤 보낸다) |
| `POST /t/{t}/volumes` | `{opId, kind:"managed", name, app, node, uid, gid(둘 다 root 아님), mode?("0750" 기본, 0700/0770), capacityBytes?(1 TiB까지)}` → `begin-volume-create`(그 앱 이름 공간, 서버가 디렉터리를 만듦) |
| | `{opId, kind:"fixed", name, node, storage, path, capacityBytes?, rootGeneration?}` → `register-fixed-volume`(승인된 저장 경로 아래 이미 있는 디렉터리, 데이터는 만들거나 지우지 않음). 저장 경로를 읽을 수 있는 시스템 관리자는 generation을 데몬이 채우고, 작업 공간 허용·꺼내는 중 여부를 미리 본다. 다른 사람은 `node-storage`를 못 읽으므로 `rootGeneration`을 넣어야 하고, 없으면 422 `storage-root-unknown` |
| `POST /t/{t}/vault` | `{opId, realm?(이 작업 공간만), parent, id, kind:"group"\|"secret", profile?, object?, keys?(secret은 1~64개)}` → `vault-create`. 이름·위치·키 이름만 만든다. 값 넣기는 아래 `vault/value`(SecretInput). Expected는 보관함 tree revision(`VaultTreeRevision`) |

### 비밀값 객체 정책 (UI-70)

데몬이 `vault` 행에서 객체의 revision을 읽어 Expected로 넣는다(본문 `expected`가 있으면 그 값). 응답은 `{op}`, target은 `vault/<path>`. 권한과 상태 판단은 mydcd가 한다(ManageSecrets, 폐기는 정리 권한).

vault 행에는 다음 칸이 더 붙는다.
- `id`, `parent`: mydcd 객체 ID와 부모. 뿌리 묶음의 ID는 작업 공간 이름이다.
- `status`: active / password-pending / revoking / retired / reference-pending 중 하나.
- `acl`: `{users, services, denyUsers, denyServices, tenantGrants?}`, 이름 목록이다. 읽기와 쓰기를 따로 주는 칸은 mydcd에 없다.
- `pendingWrite?`, `maxApprovalAge?`(초, 묶음만).

| 끝점 | 본문 → action |
|---|---|
| `PUT /t/{t}/vault/acl` | `{opId, id, users, services, denyUsers, denyServices, expected?}` → `vault-acl`(목록 전체 바꾸기). active가 아니면 409 `not-active` |
| `POST /t/{t}/vault/move` | `{opId, id, parent, expected?}` → `vault-move`. parent는 묶음 ID, 뿌리는 작업 공간 이름 |
| `PUT /t/{t}/vault/approval-age` | `{opId, id, seconds(0 = 제한 없음, 366일까지), expected?}` → `vault-approval-age`. 묶음이 아니면 409 `not-group` |
| `POST /t/{t}/vault/revoke` | `{opId, id, expected?}` → `vault-revoke`(revoking으로. 새 사용이 막힌다) |
| `POST /t/{t}/vault/retire` | `{opId, id, expected?}` → `vault-retire`. revoking이 아니면 409 `not-revoking`. 아래에 남은 것, 진행 중인 쓰기, 살아 있는 사용이 있으면 mydcd가 op `failed`로 거절한다 |

**쓰는 곳**: `GET /t/{t}/vault/usages?id=&after=` → `{items:[{id, tenant, user?, app?, standalone?, deployment?, service?, node, purpose?, generation, secrets:[비밀값 ID], live}], next, revision, asOf}`. mydcd `PublicRead` `vault-usages` 한 쪽(8행, `next`는 다음 `after`로만 넘김, `revision`은 Vault root). 그 객체에서 비밀값을 받는 앱 서비스·단독 컨테이너다. 묶음 ID면 그 아래 비밀값을 쓰는 것까지 나온다. 예전 `selector`는 mydcd가 주지 않아 빠졌다. id를 빼면 작업 공간 전체다. 클러스터 보관함은 `GET /vault/usages?id=`이고, 여기서는 id가 꼭 있어야 한다(없으면 400). 내린 앱은 `live:false`로 남거나 목록에서 빠진다. `live:true`가 있으면 mydcd가 `vault-retire`를 거절한다. 권한과 오류는 목록과 같다(mydcd가 정한다. 없는 id는 404).

묶음 승인 끝점은 [비밀번호 묶음 승인 (UI-72)](06-app-yaml-up.md#비밀번호-묶음-승인-ui-72)에 있다.

### 비밀값 값 넣기와 묶음 비밀번호 (SecretInput 중계)

mydcd의 보관함 쓰기 절차를 CLI(`mydc secret put`, `secret group password`)와 같은 순서로 한 web `opId` 아래에서 돈다: `vault-write-plan`(조회) → `vault-prepare-write` → `vault-dispatch-write` → **SecretInput**으로 계획의 받는 서버에 값 보내기 → `vault-observe-write`(받는 서버가 서명한 공개 관측) → `vault-publish-write`. 원본 네 개는 각각 서명 → 저장 → 보내기이고, 작업 목록에 `<opId>.0`~`.3`으로 남는다(부모 op에는 원본이 없어서 `/ops/{opId}/result`·`resume`은 409 `job`). **값과 비밀번호는 bbolt·로그·원본·op digest 어디에도 남지 않는다.** 요청이 끝나면 버린다. 비밀번호는 데몬이 CLI와 같이 Argon2id로 해시해 `verifier` 값으로만 보낸다.

| 끝점 | 본문 → 부모 op |
|---|---|
| `POST /t/{t}/vault/value` | `{opId, path("db/mysql"), values:{키: 값}(128개·16 KiB까지), keys?}` → `vault-value`(target = path). `keys`를 안 주면 values의 키다. 적용되면 mydcd는 쓴 키를 그 비밀값의 키로 새로 정한다(목록 행 `keys`). 첫 값을 쓰기 전 비밀값은 `reference-pending`이다 |
| `POST /t/{t}/vault/password` | `{opId, path("root/billing"), password(한 줄, 1024바이트까지), profile?}` → `vault-password`. 처음 정할 때는 `profile`(비밀번호 검증값을 쓸 쓰기 프로필, 예: `auth`)이 있어야 한다. 없으면 mydcd가 거절한다(403). 그 뒤로는 묶음이 가진 프로필을 쓴다. `profile`은 계획할 때만 쓰므로 같은 `opId`를 다시 보낼 때는 없어도 된다. 묶음에 비밀번호를 정하거나 바꾼다. 적용되면 그 묶음은 보호된다(목록 행 `protected:true`): 앱이 그 아래 비밀값을 쓰려면 권한 있는 사람이 이 비밀번호로 승인한다. 승인하는 사람 목록은 mydcd에 없다 |

첫 요청에는 값(비밀번호)이 있어야 한다(없으면 400). 같은 `opId`로 다시 보내면 멈춘 곳부터 잇는다(같은 path·keys가 아니면 409 `op-conflict`). 값은 이을 때 다시 필요할 때만 쓴다. 부모 op의 `errorCode`:

- `needs-input`(`running`): 보내기 직전에 멈췄다. 같은 opId로 값을 다시 보낸다.
- `input-unknown`(`unknown`): 값을 보냈는지 모른다. 같은 opId로 다시 보내면 **값 없이** 결과만 확인한다(값은 두 번 보내지 않는다). 아무것도 닿지 않았으면 `failed` `write-not-applied`이고, 새 opId로 다시 넣는다.
- `step-unknown`: 단계 원본의 결과를 모른다. `/ops/<opId>.<n>/result`로 정한 뒤 다시 보낸다.
- `write-not-applied`, `write-changed`, `observation-mismatch`, `no-receiver`, `result-<코드>`(단계 원본이 적용되지 않음): `failed`.

가짜 어댑터: 위 action을 실제 페이로드 형식으로 받아 목록 행만 만든다(주소 배정·실제 디렉터리·DNS 서버·값 저장은 흉내 내지 않음). 보관함 쓰기는 다섯 단계의 상태와 서명된 관측을 흉내 내고, 받는 서버에 닿은 키 이름만 기억한다(값은 버린다). 망 행에는 DNS 정책을 한 번이라도 정했으면 `dns:{zone, enabled, revision, upstreams:["1.1.1.1:53"], ttl, negativeTtl, reverse}`가 붙고, DNS가 켜져 있으면 각 `members[]`에 `resolver`(망 안에서 이름을 묻는 주소, 가짜에서는 그 서버 주소 묶음의 gateway)가 붙는다. `mydc.Page.Collection`이 Expected로 쓰는 revision이다(resources는 망 목록, vault는 tree).

아직 없는 것: 보호된 묶음의 승인(`vault-approval-plan`·SecretInput approve, 앱 배포 화면에서), 실제 mydcd에 SecretInput을 보내는 어댑터(받는 서버로 직접 연결), 망 구성원 바꾸기(`reconfigure-tun-network`)·망·데이터 저장소·보관함의 바꾸기·지우기 전용 끝점(지금은 `/ops`), 작업 공간 관리자용 저장 경로 목록.

### 클러스터 보관함 (UI-70 '클러스터 보관함' 토글)

CLI `mydc secret --cluster`와 같은 클러스터 범위 보관함(mydcd realm `""`)이다. **mydcd 몫**: 권한(시스템 관리자만), tree 상태, 쓰기 절차. **웹 몫**: 작업 공간 보관함(`/t/{t}/vault…`)과 같은 끝점을 작업 공간 없이 `/vault…`에서 realm `""`로 돌리는 것뿐이다. 행의 `realm`은 `""`다(`"cluster"`가 아니다). 웹은 권한을 따로 판단하지 않는다. 시스템 관리자가 아니면 mydcd가 거절한다(목록 403, 바꾸기는 op `failed` forbidden).

| 끝점 | 뜻 |
|---|---|
| `GET /vault?after=` | `{items, next, revision, asOf, initialized, root?}`. items는 작업 공간 보관함 행과 같고 `realm:""`이다. 뿌리 묶음도 한 행으로 온다(`parent:""`). `initialized:false`면 아직 클러스터 보관함이 없다. `root`는 뿌리 묶음 ID(맨 위 객체의 parent) |
| `POST /vault/init` | `{opId, root?}` → `vault-init {Realm:"", Root}`(Expected 0). root 기본 `"cluster"`. 이미 있으면 409 `exists` |
| `POST /vault` | 작업 공간의 `POST /t/{t}/vault`와 같다(만들기). parent는 묶음 ID 또는 `root`. `realm`을 주면 `""`만 된다(아니면 422) |
| `POST /vault/value`, `/password` | 값 넣기·묶음 비밀번호. 작업 공간과 같은 절차·오류 코드 |
| `PUT /vault/acl`, `POST /vault/move`, `PUT /vault/approval-age`, `POST /vault/revoke`, `/retire` | 객체 정책. 작업 공간과 같다. move의 뿌리는 `root` |

작업 공간 보관함 목록(`/t/{t}/vault`)에는 클러스터 행이 나오지 않는다. 클러스터 보관함 작업은 `tenant`가 빈 op로 남는다. 묶음 승인(UI-72)은 아직 작업 공간 보관함만 다룬다.

가짜 어댑터: 처음에는 클러스터 보관함이 없다. `vault-init`은 클러스터 realm만 받는다(작업 공간 tree는 고정 데이터에 이미 있다). realm `""`의 읽기·바꾸기는 시스템 관리자만 된다.
