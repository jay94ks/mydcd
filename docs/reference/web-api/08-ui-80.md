## 내장 저장소 (UI-80)

`sfcli registry`와 `manage apply`의 `put/start/stop/delete-registry`와 같다. 정의 검사, Volume 확인, 서버별 권한은 sfcd가 맡는다. 모든 변경은 `{op}`를 돌려준다.

- `GET /t/{t}/registries?after=` → `{items, next, revision, asOf}`. 행: `id`, `name`, `endpoint`(TLS authority), `node`, `address`, `certificateID`(노드가 지금 쓴다고 보고한 보관함 인증서 ID, hex; 보고 전에는 없음), `volume`, `enabled`, `active`, `deleted`, `draining`, `observedAt`(Unix ms), `revision`(모든 변경의 expected), `generation`, `repositories`, `limits`, `status`.
  - `status`는 CLI와 같다: `serving`(서버가 지금 정의로 돌고 있다고 보고함, 외부 TLS 검사는 아님), `pending`(켜졌지만 아직 보고 없음), `draining`, `stopping`, `stopped`, `deleted`. 켜져 있다는 것(`enabled`)과 실제로 돈다는 것(`serving`)은 다르다.
  - `limits`: `{metadata:{manifestBytes, records, totalBytes}, blobs:{blobBytes, totalBytes, records}, budget:{cpu(1e9 = 1코어), memory}, maxRequests, maxHeaderBytes, requestTimeoutMS, tokenSeconds}`.
- `PUT /t/{t}/registries/{id}` `{opId, node?, authority?, address?, volume?, enabled?, limits?, expected?}` → `put-registry`.
  - 새 ID는 `authority`·`volume`이 필요하다(TLS 인증서는 authority 호스트로 보관함에서 찾는다)(없으면 422). volume은 이 작업 공간의 보존 고정 데이터 저장소 이름이다(없으면 404). 보존 고정이 아니거나 서버가 맞지 않으면 sfcd가 거절해 op가 `failed`다. 기본값: node는 그 저장소의 서버, address는 `0.0.0.0:<authority 포트, 없으면 443>`, enabled는 true, limits의 blob 총량은 저장소 용량, 나머지는 위 기본값.
  - 있는 ID는 보내지 않은 값을 그대로 둔다. volume은 바꿀 수 없다(422). 지운 ID는 409 `deleted`.
  - 정의가 맞지 않으면 422다(authority 포트와 address 포트가 같아야 한다). 저장소를 만들어도 이미지 신뢰 출처가 추가되지는 않는다.
- `POST /t/{t}/registries/{id}/{start|stop|delete}` `{opId, expected?}`. stop과 delete는 데이터 저장소의 데이터를 남긴다. delete는 멈춘 뒤에만 된다(409 `not-stopped`). 없는 ID는 404.
- 접근 자격(UI-81, `sfcli registry login`): `POST /t/{t}/registries/{id}/credential` `{repository, access?}` → `{registry, authority, username, token, repository, access:[...], expiresAt}`. op가 아니라 바로 응답한다.
  - `repository`는 이미지 경로(예: `shop/web`), `access`는 `pull`(기본)·`push`·`pull,push`. 아니면 422.
  - `docker login <authority> -u <username> --password-stdin`에 `token`을 넣어 쓴다. 만료는 저장소의 토큰 시간과 세션 만료 중 이른 쪽이다.
  - 누가 받을 수 있는지는 sfcd가 정한다(pull은 배포 권한, push는 저장소 관리 권한). 멈춘 저장소나 권한이 없으면 403.
  - 토큰은 이 응답 본문(`Cache-Control: no-store`)에만 나간다. 데몬은 bbolt·작업 기록·로그·op 어디에도 남기지 않는다. 화면도 한 번 보여 주고 버린다.

### 저장소 이미지와 정리 (UI-84, UI-8A, sfcd 실제 계약 REQ-18)

계약은 `docs/reference/registry-images.md`(`registry-catalog`), `image-usages.md`, `registry-maintenance.md`(`registry-maintenance-plan`·`-status`, `registry-prune-preview`·`-results`, action `delete-registry-image`·`gc-registry`·`prune-registry-images`)다. 목록, 쓰는 곳 판단, 권한, 삭제는 sfcd가 한다. 웹이 더하는 것은 두 가지다: 목록 쪽을 잠깐 기억하는 메모리 캐시, 그리고 웹이 보관한 내린 앱(bbolt)이 쓰는 이미지. 읽기는 작업 공간 Read, 삭제·GC·정리와 그 미리 보기는 저장소 관리 권한이 필요하다.

삭제·GC·정리 op의 `applied`는 **작업 수락**일 뿐이다. 실제 진행은 `GET /t/{t}/registry-maintenance/web-<opId>`로 본다(웹 작업의 안정적인 작업 ID가 `web-<opId>`). 웹은 계획의 `Expected`와 maintenance root revision으로 서명한다.

- `GET /t/{t}/registries/{id}/images?external=1&repository=&after=&refresh=1` → `{kind(managed/external), id, authority, repository?, code?, live, untaggedComplete, repositories, items, next, asOf, cachedAt}` (한 쪽 8행).
  - `repository`가 없으면 `repositories`(저장소 이름)만, 있으면 그 저장소의 `items`가 온다. 행: `{repository, reference(태그 또는 digest 자체), digest, mediaType, manifestBytes, imageBytes, uploadedAt?}`. 한 digest에 태그 행이 여럿일 수 있고, 내장 저장소는 digest 자체 행도 준다. 이미지 수·용량은 digest로 묶어 센다. `uploadedAt`은 sfcd가 아는 경우에만 있다(외부 저장소는 없음).
  - `external=1`이면 `{id}`는 외부 저장소 정의이고, 읽는 서버가 연결돼 있어야 한다. 외부 목록은 `live:true`다(쪽 사이에 태그가 바뀔 수 있음).
  - `code`가 있으면 목록을 못 읽은 까닭이다(`unauthorized`, `denied`, `not-found`, `unsupported`, `unavailable` 등). 그때는 행이 없다.
  - 같은 사용자가 같은 쪽을 10분 안에 다시 읽으면 데몬 메모리에서 준다(캐시는 사용자마다 따로). `cachedAt`은 sfcd가 답한 때다. `refresh=1`이면 바로 sfcd를 읽는다. 캐시에서 줄 때도 sfcd에 작업 공간 읽기 권한을 먼저 묻는다(없으면 403). 캐시는 bbolt에 남기지 않는다. 이 웹으로 보낸 삭제·GC·정리는 그 저장소의 캐시를 지운다.
- `POST /t/{t}/image-usage` `{refs:[ref 또는 sha256 digest, 1..32개]}` → `{items:[{ref, rows, truncated, archived}]}`. 요청 순서와 같고 ref마다 `image-usages`를 읽는다(256행까지, 넘으면 `truncated`).
  - `rows`: `[{id, app?, deployment?, node?, service?, instance?, image?, kind, task?, operation?, version?, unknown?, match}]`. `kind`는 sfcd 값(`app-execution`, `cd-candidate`, `app-previous` …), `match`는 `exact`, `digest`, `repository-unknown`(태그와 digest의 대응을 모름: 같은 저장소의 다른 태그일 수도 있다), `unknown`, `scope`다. 행 수는 컨테이너 수가 아니다.
  - `archived`: `[{key, app, image, downAt}]`, 내린 앱 중 app.yaml의 `services.*.image`가 같은 이름(digest로 물으면 같은 digest)을 가리키는 것. `key`는 `/t/{t}/archived/{key}`의 key다. `${...}`가 든 image는 보지 않는다.
- `POST /t/{t}/registries/{id}/images/delete` `{opId, external?, repository, reference, digest}` → `{op}` (`delete-registry-image`). `reference`가 태그면 그 태그만, digest면 그 이미지와 모든 태그를 지운다. `digest`는 화면이 본 이미지다(그 사이 태그가 다른 digest로 옮겨 갔으면 결과 `reference-changed`). 형식이 틀리면 422.
  - sfcd 계획이 쓰는 곳이 있다고 하면 보내지 않고 409 `image-in-use`. 저장소에 끝나지 않은 작업이 있거나 서비스 중이 아니면 409 `busy`.
  - 외부 저장소는 digest 삭제만 된다(태그만 지우기는 결과 `unsupported`).
  - 내린 앱만 쓰는 이미지는 막지 않는다. 화면이 `image-usage`의 `archived`로 먼저 알린다.
- `POST /t/{t}/registries/{id}/gc` `{opId}` → `{op}` (`gc-registry`, 내장 저장소만). 쓰지 않는 blob을 회수한다. 끝나지 않은 작업이 있으면 409 `busy`. 마지막 GC와 진행 중 작업은 `GET /t/{t}/registries` 행의 `maintenance{pendingOperation?, pendingState?, lastGCOperation?, lastGCAt?(Unix 밀리초), reclaimedBytes}`에 있다.
- `GET /t/{t}/registry-maintenance/{operation}` → `{operation, action, user, state, revision, at, registry, external, repository?, reference?, digest?, result?}`.
  - `state`: `queued` → `running` → `done` 또는 `failed`. `unknown`은 외부 DELETE 응답을 잃은 경우로, 끝나지 않는다.
  - `result`: `{code, at, reclaimedBytes, native?, prune?{processed, deleted, skipped, failed, gcCode?, gcAt?}}`. `code`는 `ok`, `already-absent`, `image-in-use`, `reference-changed`, `denied`, `uploads-in-progress`, `registry-budget`, `partial`, `preview-unavailable` 등이다.
- 조건으로 정리(일괄):
  - `POST /t/{t}/registries/{id}/prune/preview` `{external?, part(items/retained), conditions, preview?, after?}` → `{conditions, preview, items, retained, imageBytes, estimatedReclaimedBytes, estimateKnown, live, expiresAt, part, total, processed, rows, retainedRows, next}` (`registry-prune-preview`, 한 쪽 8행). 지우지 않는 미리 보기다.
  - `conditions`: `{repositories?(빈 배열이면 전부, 256개까지), keepRecentPerRepository(저장소마다 남길 최근 태그 수), before?(Unix 초, 이보다 늦게 올린 것은 남김), excludeTags?(path.Match 패턴, `/` 없이 32개까지), includeUntagged?, protectedDigests?, gc?(내장 저장소만)}`. 목록은 데몬이 정렬한다. 범위를 벗어나면 422.
  - 첫 쪽(`preview` 없이)에서 데몬이 내린 앱이 쓰는 digest를 `protectedDigests`에 더하고(태그면 `image-resolve`로 digest를 푼다), 응답의 `conditions`와 `preview`(서명된 미리 보기 토큰)를 준다. 다음 쪽과 다른 part는 그 `conditions`와 `preview`를 그대로 보낸다(part를 바꿀 때는 after를 비운다). 미리 보기는 10분 유효하다(`expiresAt`). 지났거나 저장소가 바뀌었으면 409 `preview-expired`.
  - `rows`: `[{id, image, aliases(태그 수), aliasDigest}]`. `retainedRows`: `[{image, code}]`, code는 `image-in-use`, `protected`, `excluded-tag`, `recent`, `upload-time-unknown`, `too-recent`, `untagged-excluded`, `manifest-dependency`, `repository-filter`.
  - `POST /t/{t}/registries/{id}/prune` `{opId, external?, conditions, preview}` → `{op}` (`prune-registry-images`). 미리 보기의 계획으로 항목 전부와 선택 GC를 한 작업으로 보낸다. 실행 직전 쓰이기 시작한 항목은 sfcd가 건너뛴다.
  - `GET /t/{t}/registry-maintenance/{operation}/items?after=` → 같은 모양이고, `rows`에 항목마다 `code`·`at`이 붙는다(`registry-prune-results`).

### 이미지 올리기·레이어 보기·태그 추가 (UI-88, UI-89)

웹 데몬이 내장 저장소의 표준 저장소 API(토큰 흐름, blob, manifest)를 직접 쓴다. 누가 받고 올릴 수 있는지는 sfcd가 정한다. 데몬은 단계마다 sfcd에 그 저장소 하나로 범위를 좁힌 짧은 자격(`registry-credential`, pull 또는 pull,push)을 받아 쓴다. 자격이 거절되면 403이다. 자격은 브라우저에 주지 않고, bbolt·로그·작업 기록 어디에도 남기지 않는다. 저장소 토큰이 끝나면 새 자격을 받아 이어 간다. 이 변경들은 op가 아니다(서명 원본이 없다). 쓰기가 끝나면 그 저장소의 목록 캐시를 지운다.

- 올리기(UI-88). 압축 파일은 웹 데이터 폴더(`image-uploads/`)에 하루 동안 남고, 사용자마다 3개까지다. 만들기는 sfcd가 알려 준 역할이 작업 공간 관리자일 때만 된다(웹 디스크를 쓰기 때문이다. 실제 올리기 권한은 그때 받는 push 자격이 정한다).
  - `POST /t/{t}/registries/{id}/uploads` `{fileName, bytes(≤10 GiB)}` → 201 U. 조각은 `chunkBytes`(8 MiB)씩이고 마지막 조각만 짧다.
  - `PUT …/uploads/{uid}/chunks/{n}`: 본문이 조각 원본이고, 길이가 정확히 맞아야 한다(아니면 400). 다시 보내면 덮어쓴다. 응답은 `{received, missing}`다. 새로 고침 뒤에는 `GET …/uploads`로 내 올리기를 찾고, `missing`에 있는 조각만 다시 보낸다.
  - `GET …/uploads` → `{items:[U]}`, `GET …/uploads/{uid}` → U, `DELETE …/uploads/{uid}` → 204(진행 중인 push도 멈춘다). 다른 사람의 올리기는 404다.
  - `POST …/uploads/{uid}/inspect` → 202. 모든 조각이 와야 한다(아니면 409 `incomplete`). U의 `inspect.state`가 `done`이 될 때까지 다시 읽는다. done이면 `inspect.items:[{index, kind(image/index), refs(묶음 안의 이름), platforms, bytes, layers, digest?}]`가 있고, failed면 `inspect.error`가 있다.
  - 형식: `docker save`(옛 manifest.json, 또는 Docker 25+의 OCI 배치)와 OCI image layout이고, `.tar`·`.tar.gz`·`.tgz`를 받는다. `.tar.zst`는 아직 안 된다. 압축을 풀 zstd 라이브러리가 없고, 새 의존성은 따로 정할 일이라서다. 여러 플랫폼 묶음에서 일부 플랫폼만 들어 있으면 들어 있는 플랫폼을 하나씩 따로 보여 준다. 옛 docker save의 레이어는 압축 없이 OCI manifest로 올린다.
  - `POST …/uploads/{uid}/push` `{item, repository, tag, overwrite?}` → 202. U의 `push.state`가 preparing/pushing에서 done/failed/canceled가 될 때까지 다시 읽는다. `push.layers:[{digest, bytes, done, state(waiting/checking/skipped/uploading/uploaded)}]`에서 skipped는 저장소에 이미 있어 건너뛴 것이다. 끝나면 `push.digest`(manifest digest)가 있고, 실패면 `push.error`가 있다.
  - 그 태그가 이미 다른 이미지를 가리키고 overwrite가 아니면 409 `tag-exists` `{current, usage}`다. usage는 `image-usage`의 items 한 개와 같은 모양이다.
  - U = `{id, registry, fileName, bytes, chunkBytes, chunks, received, missing(앞 200개), createdAt, expiresAt, inspect?, push?}`.
- 레이어 보기(UI-89):
  - `GET /t/{t}/registries/{id}/images/manifest?repository=&ref=&platform=` → `{repository, ref, digest, mediaType, manifest(원본 JSON), config?(원본 JSON), platforms?, history:[{created?, createdBy?, comment?, emptyLayer?}], layers:[{digest, mediaType, bytes, createdBy?}]}`. ref는 태그나 digest다. 여러 플랫폼 묶음이면 `platforms:[{platform, digest}]`만 오고, `platform=os/arch`를 주면 그 이미지를 연다. `createdBy`는 history와 레이어 수가 맞을 때만 붙는다.
  - `GET …/images/layer?repository=&digest=` → `{digest, files:[{path, bytes, mode, type(file/dir/symlink/hardlink/other), link?, whiteout?}], truncated}`. 그 레이어가 더하거나 바꾸거나 지우는(whiteout) 파일 목록이고 5만 개까지다. 웹이 digest별로 데이터 폴더(`layer-index/`)에 기억해 둔다. 기억한 목록도 그 사용자의 pull 자격으로 저장소에 레이어가 있는지 확인한 뒤에만 준다. 없으면 404다. zstd 레이어는 아직 못 본다.
- 태그 추가: `POST /t/{t}/registries/{id}/images/tag` `{repository, digest, tag, overwrite?}` → `{repository, tag, digest}`. 같은 digest의 manifest를 새 태그로 다시 올린다. 이미 같은 digest를 가리키면 아무것도 하지 않는다. 다른 이미지를 가리키면 409 `tag-exists` `{current, usage}`다.
