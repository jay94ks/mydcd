## 데이터 저장소 백업·복원·용량·삭제 (UI-60·62·63)

데몬이 저장소 행(`volumes`의 scope·native binding), 백업 행(`volume-backups`), 복원 행(`volume-restores`), 백업 출처(`volume-backup-source`)에서 payload를 만든다. 응답은 `{op}`, `opId` 규칙은 공유 자원 만들기와 같다(target `volume/<이름>`). 권한과 상태 판단은 sfcd가 한다. 이름이 같은 저장소가 여러 앱에 있으면 409 `ambiguous`이고, 본문(또는 GET의 쿼리)에 `app`을 준다.

| 끝점 | 본문 → action |
|---|---|
| `GET /t/{t}/volumes/{name}?app=` | `{volume, backups:[B], restores:[R], archives:[A], archiveReady}`. volume은 목록 행과 같고 `phase?`, `moveID?`, `targetNode?`, `movePhase?`, `archiveID?`, `archivePhase?`, `retained?:[{moveID, node, state}]`가 붙는다. 보관이 잡고 있는 동안 `phase`는 `Archived`다. `archiveReady`는 클러스터 키와 관리자 키가 둘 다 있어 "보관"을 보일 수 있을 때다. 없으면 404 `not-found` |
| `POST /t/{t}/volumes/{name}/backups` | `{opId, app?, id?, maxBytes?, maxEntries?}` → `begin-volume-backup`. id 기본 `"b-" + opId`. maxBytes(임시 보관 예약) 기본은 용량, 용량이 없으면 사용량×2(최소 1 GiB), 최대 1 TiB. **앱에 딸린 저장소만** 된다(아니면 409 `no-app`). Expected는 데몬이 백업 출처에서 읽은 저장소 revision |
| `POST …/backups/{id}/cancel` | `{opId, app?}` → `cancel-volume-backup`. `Reserved`일 때만 적용된다 |
| `DELETE …/backups/{id}` | `{opId, app?}` → `delete-volume-backup`. `Ready`이고 진행 중인 복원이 없을 때만 적용된다 |
| `POST /t/{t}/volumes/{name}/restore` | `{opId, app?, backup, target:{name, app?}, capacityBytes?}` → `begin-volume-restore`. **새 저장소로만** 복원한다(`target.existing:true`는 422 `restore-new-only`). 새 저장소는 백업이 있는 서버에 만들어지고, app 기본은 백업한 앱이다. 백업이 `Ready`가 아니면 409 `backup-not-ready`. 복원 ID는 `"r-" + opId 앞 8자`. 복원 예약(MaxBytes)은 sfcd 하한과 같은 `DataBytes + 항목 수 × 8 KiB`이고, 1 TiB를 넘으면 422 `restore-too-large`. `capacityBytes`는 이 값 이상 1 TiB 이하(아니면 422) |
| `POST …/restores/{id}/cancel` | `{opId, app?}` → `cancel-volume-restore`. `Reserved`일 때만 적용된다 |
| `POST /t/{t}/volumes/{name}/archive` | `{opId, app?, id?, store?, compress?, maxBytes?, maxEntries?}` → `archive-volume`(내린 앱의 저장소 보관). id 기본 `"a-" + opId`. store(저장 경로) 기본은 그 서버의 기본 보관 위치, 없으면 `default` 저장 경로. compress 기본 true(zstd), false면 압축하지 않고 봉인만 한다. maxBytes 기본은 백업과 같다. **앱에 딸린 저장소만**(409 `no-app`). 키가 없으면 409 `archive-keys`. 앱이 내려가 있지 않거나, 쓰던 컨테이너가 정상 종료하지 않았거나, 진행 중인 이동·백업이 있으면 op `failed` |
| `POST /t/{t}/volumes/{name}/unarchive` | `{opId, app?, id?}` → `unarchive-volume`. id 기본은 저장소를 잡고 있는 보관. `Archived`일 때만 적용된다. 풀다가 실패하면 보관은 다시 `Archived`가 되고 `failure`가 붙는다(묶음은 남음) |
| `POST …/archives/{id}/cancel` | `{opId, app?}` → `cancel-volume-archive`. `Packing`일 때만 적용된다 |
| `DELETE …/archives/{id}` | `{opId, app?}` → `discard-volume-archive`. `Archived`일 때만 적용된다. 묶음을 지우고 저장소는 빈 채로 풀린다. 그다음 저장소 삭제를 따로 보낸다 |
| `PUT /t/{t}/volumes/{name}/capacity` | `{opId, app?, bytes}` → `set-volume-capacity`. **시스템 관리자만**, **늘리기만** 된다(줄이면 422 `capacity-grow-only`, 작업 공간 관리자는 op `failed` forbidden) |
| `DELETE /t/{t}/volumes/{name}` | `{opId, app?}` → `delete-volume`(고정 저장소는 `unregister-fixed-volume`, 디스크의 데이터는 남는다). 쓰는 컨테이너가 있으면 op `failed`. sfcd는 지운 저장소를 `Deleted` 행으로 남기지만, 데몬은 그 행을 저장소 목록에서 빼고 상세는 404 `not-found`로 답한다 |
| `GET /t/{t}/backup-limits?node=` | `{items:[{node, scope(workspace/server), hidden, count, bytes, stagingCount, stagingBytes, revision, used:{count, bytes, stagingCount, stagingBytes}}]}` (REQ-34 `PublicRead` `volume-backup-limits`). 작업 공간 행을 읽고, 서버 전체 행은 같은 읽기를 작업 공간 없이 한 번 더 한다(시스템 관리자만 받는다). 그 밖의 사람에게는 작업 공간 행의 GlobalPresent로 `hidden:true` 행만 온다. `used`는 실제 디스크 측정치가 아니라 sfcd가 백업·복원·옮기기 예산에 잡아 둔 양이다 |
| `PUT /t/{t}/backup-limits/{node}` | `{opId, scope?(workspace 기본·server), count, bytes, stagingCount?, stagingBytes?, expected?}` → `set-volume-backup-limit`(시스템 관리자만). Expected 기본은 지금 행 revision(없으면 0). 행에 Original(옮기기 예산)이 있으면 그대로 실어 보낸다(REQ-66, `PublicRead` 행의 `Original`). 이미 잡힌 양보다 작게 하면 op `failed` |
| `GET /t/{t}/volumes/{name}/users?app=` | `volume-users`: 이 저장소를 붙인 앱 서비스·단독 컨테이너. `{tenant, network|volume, users:[{kind, app?, service?, standalone?, node?, consumer?, readOnly, attached, selection?}], apps, standalones, total}`. sfcd `PublicRead`의 `network-users`·`volume-users` 행(작업 하나에 한 행)을 앱 서비스(또는 단독 컨테이너)·서버마다 하나로 묶는다. `kind`는 `service`(sfcd 작업 kind `app`)·`standalone`·`volume-operation`(백업·옮기기가 읽는 중, `consumer`가 그 ID). `attached`는 망이면 sfcd가 그 컨테이너의 망 연결(EndpointPresent)을 확인했을 때, 저장소면 컨테이너가 있을 때다. `readOnly`는 하나라도 읽기 전용 consumer일 때. `selection`은 있는 컨테이너마다 `{app, service}` 또는 `{standalone}` 하나다. 페이지 cursor는 해석하지 않고 다음 After로만 넘기며, 64쪽(512행)을 넘으면 502 `public-read-too-long`. 관측 시각(`observedAt`)은 sfcd가 주지 않아 빠졌다 |

B = `{key, tenant, volume, id, node, phase, revision, bytes, createdAt, failure?}`(createdAt은 백업 요청을 서명한 Unix 초), phase는 `Reserved` → `Ready`/`Failed`, 취소는 `Cancelling` → `Cancelled`, 지우기는 `Deleting` → `Deleted`. R = `{key, tenant, volume, backup, id, node, phase, target, revision, maxBytes, capacityBytes?}`, phase는 `Reserved`/`Cancelling`/`Restored`/`Cancelled`.

A = `{id, node, store, phase, compression(zstd/none), maxBytes, tarBytes?, dataBytes?, failure?, revision}`. phase는 `Packing` → `Clearing` → `Archived` → `Restoring` → `Restored`, 취소는 `Cancelling` → `Cancelled`, 실패는 `Failed`(저장소는 그대로), 지우기는 `Discarding` → `Discarded`. sfcd는 저장소마다 끝난 보관 기록을 하나만 남긴다. tarBytes는 파일을 묶은 크기, dataBytes는 디스크의 묶음 크기다. 보관된 앱을 다시 배포하기 전에는 보관된 저장소를 모두 `unarchive`하고 `Restored`가 될 때까지 기다린다(sfcd는 보관 중인 저장소를 쓰는 배포를 받지 않는다).

sfcd는 그 서버의 서버 전체 백업 한도와 작업 공간 한도가 둘 다 있어야 새 백업·복원을 받는다. 하나라도 없거나 넘치면 op가 `failed`다.
