## sfcd와 sfc-web의 책임 경계

**클러스터 상태는 전부 sfcd(와 CLI `sfcli`)가 정의·저장·확정·실행한다.** sfc-web은 화면을 서빙하고, 로그인한 사용자의 세션으로 sfcd method를 부르며, **웹 자체 데이터**만 가진다. 웹에 없는 클러스터 기능이 필요하면 웹이 대신 구현하지 않고 REQUEST.md에 REQ로 요청한다. 웹 끝점이 생겼다고 그 기능이 sfcd에 있다는 뜻은 아니다. sfcd에 아직 없는 method를 쓰는 끝점은 가짜 어댑터(mock)에서만 동작한다([상태표](../../../apps/sfc-web/CLUSTER_METHODS.md)).

| 맡는 쪽 | 하는 일 |
|---|---|
| **sfcd / sfc** | 인증·세션 발급, 권한 판단(사용자·작업 공간·Deploy/Read 등), CAS·원 작업(UserOperation) 확정과 결과, Raft·DB 저장. 앱·컨테이너·**단독 컨테이너**·망·데이터 저장소·비밀값 보관함·이미지·외부 접속의 정의·상태·실행·정산. 인증서 보관함과 외부 접속 인증서 적재. 관측(Task·로그·자원·이벤트)과 컨테이너 스트림(exec). 위임 계정. |
| **sfc-web** | 화면 파일 서빙, 브라우저 로그인 세션(쿠키)과 사용자별 sfcd 연결 유지. 화면용 입력을 sfcd의 실제 payload로 옮기고 제품 입력 검사(`control.InputChange`)를 미리 돌린 뒤, **사용자 세션으로 서명한 원본을 먼저 저장하고 보내기**(결과 불명이면 같은 원본으로만 확인). 웹 자체 데이터(bbolt): 보낸 작업 기록, 보관된 앱 app.yaml, 그래프 블록 위치·AI 가림 같은 화면 보조 자료, 웹 설정·설정 변경 기록·알림, 봉인 파일(AI·DNS 토큰, ACME 계정 키). 화면용 묶기·가공·짧은 캐시(예: 이미지 목록)와 SSE 중계. 클러스터 밖 연동: 외부 DNS 공급자, ACME 인증 기관(발급 결과는 sfcd 인증서 보관함에 넣음), AI, 웹훅 설정(클러스터 안 전달은 sfcd, REQ-24). |

지켜야 할 것:

- 웹은 클러스터 자원의 **사본·대체 상태를 만들지 않는다.** 목록·상태는 매번 sfcd에서 읽는다(웹 bbolt 행은 권한을 주지 않는다).
- 웹은 sfcd 권한을 넘거나 우회하지 않는다. 미리 하는 검사(입력 모양, 저장 경로 허용 등)는 오류를 일찍 보여 주려는 것이고, 최종 판단은 sfcd 결과다.
- 단독 컨테이너처럼 클러스터 상태를 다루는 새 기능은 sfcd method(REQ)가 먼저이고, 웹 끝점은 그 method를 부르는 얇은 층이다. 웹은 정의 원문을 해석해 컨테이너를 직접 만들거나 Docker를 부르지 않는다.
- CLI도 필요로 하는 기능은 sfcd 쪽이다.
- 내장 저장소의 이미지 올리기·레이어 보기·태그 추가(UI-88·89)는 예외로 웹이 맡는다. 웹은 `docker push`처럼 표준 저장소 API를 쓰는 사용자 쪽 프로그램일 뿐이다. 누가 받고 올릴 수 있는지는 sfcd가 저장소 하나로 범위를 좁혀 발급하는 짧은 자격이 정한다.
- 각 절의 '아직 없는 것'에는 sfcd 쪽에 필요한 것(REQ 번호)과 웹 쪽에 남은 것을 나눠 적고, PR 설명에도 어느 쪽 일인지 적는다. 작업 나누기 기준은 `devel/design/web-dev-workflow.md`의 '할 일 나누기' 절을 따른다.
