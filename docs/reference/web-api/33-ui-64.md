## 데이터 저장소 옮기기 (UI-64)

`sfcli volume move --dry-run --save-plan`·`move --plan`과 같다. **sfcd 몫**: 옮기기 계획(`app-plan-stream`의 move 요청, 앱 산출물과 `begin-volume-move` 내용), 권한(ManageVolumes·Deploy, 받는 서버), 복사·확정·전환(서버들끼리, `commit-volume-move`는 서버가 보낸다), 원본 보관과 지우기. **웹 몫**: 앱 정의에 새 서버 적기, 계획 받은 산출물 올리기와 단계 이어 하기, 서명 원본 저장 후 보내기, 묶음 승인 비밀번호 전달(남기지 않음). 웹은 옮기기 상태를 따로 저장하지 않는다. 진행은 저장소 행(`phase:"Moving"`, `moveID`, `targetNode`, `movePhase`)에서 읽는다.

| 끝점 | 뜻 |
|---|---|
| `POST /t/{t}/volumes/{name}/move-plan` | `{app?, node \| yaml, id?, maxBytes?, maxEntries?, transferSeconds?}` → `{volume, app, id, from, to, yaml, digest, capacityBytes, maxBytes, maxEntries, transferSeconds, expiresAt, cd, services}`. 바꾸지 않는다. `node`를 주면 데몬이 지금 돌고 있는 앱 정의에 `volumes.{name}.x-sfc.node: node`를 적는다(다른 줄은 그대로). 앱 정의를 직접 고치려면 `yaml`을 준다. `digest`는 쓴 앱 정의(yaml)의 SHA-256이다. maxBytes(옮길 자료 상한) 기본은 용량, maxEntries 기본 100000, transferSeconds(복사 마감) 기본 900, 최대 86400. 응답의 `transferSeconds`는 요청한 값이고, sfcd가 정한 마감은 `expiresAt`이다. 앱에 딸린 저장소만 된다(409 `no-app`). 이미 옮기는 중이면 409 `moving`, 앱이 내려가 있으면 409 `app-not-running`. `cd:true`면 앱이 자동 배포 중이다(아래 승인) |
| `POST /t/{t}/volumes/{name}/move` | `{opId, app?, node \| yaml, digest?, id?, maxBytes?, maxEntries?, transferSeconds?}` → `{op}`(action `volume-move`, target = 저장소 이름, `move:{volume, id, from, to, cd?}`). 단계: `begin-app-upload` → `put-app-part` × n → `begin-volume-move`(Expected는 sfcd 계획의 저장소 revision) → 묶음 승인. 옮기기 ID 기본 `"mv-" + opId`. 계획 때 받은 `digest`를 주면 그 사이 앱 정의가 바뀐 경우 409 `digest-mismatch`. 같은 opId·같은 내용으로 다시 보내면 이어 간다(배포와 같음). 계획 산출물이 요청과 맞지 않으면 502 `plan-invalid` |
| `POST /t/{t}/volumes/{name}/move/cancel` | `{opId, app?, id?}` → `cancel-volume-move`. id 기본은 지금 옮기는 것. 옮기는 중이 아니거나 id가 다르면 409 `not-moving`. 확정(OwnerCommitted) 뒤에는 sfcd가 거절한다(op `failed`) |
| `DELETE /t/{t}/volumes/{name}/retained/{id}` | `{opId, app?}` → `delete-retained-volume`: 끝난 옮기기가 남긴 원본을 지운다. 이미 지우는 중이거나 없어졌으면 409 `not-retained` |

- **묶음 승인**: 옮기기는 먼저 접수(`begin-volume-move` 적용)되고, 그 원본으로 묶음 승인을 받는다(CLI와 같은 순서). 기다리는 동안 op는 202, `state:"running"`, `errorCode:"approval-required"`, `approvals`가 붙는다. 비밀번호는 배포와 같은 `POST /t/{t}/apps/deploy/{opId}/approve`로 보낸다. `GET /t/{t}/vault/approvals`에도 나온다. 승인이 끝나면 op는 `applied`이고, 서버들이 복사를 시작한다. 승인이 없으면 sfcd가 옮긴 앱을 띄우지 않는다.
- **자동 배포 앱**(`cd:true`): 옮긴 사람이 아니라 CD를 등록한 사람이 `GET/POST /t/{t}/apps/{app}/cd/approvals?operation={옮기기 ID}`로 승인한다. 이 op는 `begin-volume-move`가 적용되면 바로 `applied`다.
- **남긴 원본**: 옮기기가 끝나면 원래 서버의 자료가 남는다. 저장소 행 `retained:[{moveID, node, state(retained/deleting/removed)}]`(REQ-43, sfcd `volumes` 행의 Retained). 행이 비어 있으면, 웹이 시작한 옮기기는 op 기록의 `move.id`로 지우기를 제안한다.
- 가짜 어댑터: 계획 산출물은 `{FakeBlueprint, Document}` JSON이다. 서버 일은 흉내 내지 않는다. 옮기기는 `Prepared`에 머물고, 시험은 `Fake.FinishVolumeMove`로 끝낸다(묶음 승인이 없으면 실패). 끝나면 저장소가 새 서버로 가고, 올린 앱 정의가 옮기기 ID로 돌고, 원본이 `retained`로 남는다. 취소·원본 지우기는 바로 끝난다.

옮기기 자체는 sfcd에 있는 기능만 쓴다.
