## MCP 연동 (UI-B9, W2.3a)

전부 sfc-web 몫이다. 시스템 관리자만 읽고 바꾼다(요청마다 sfcd whoami). 토큰은 봉인 저장소(`mcp-token-{name}`)에만 있고 bbolt·로그·응답에 남지 않는다(`last4`만). 도구의 응답 본문은 저장하지 않는다. 클라이언트는 Streamable HTTP(프로토콜 2025-06-18; 2025-03-26도 받음)로 `initialize` → `notifications/initialized` → `tools/list`(cursor로 10쪽, 도구 200개까지, 응답 1 MiB까지)를 부르고, JSON과 SSE 응답을 다 읽으며 `Mcp-Session-Id`를 이어 보낸다. 주소 규칙은 웹훅과 같다(https만, 사설·루프백·링크 로컬·특수 주소는 저장할 때와 접속할 때 둘 다 막고, 리다이렉트는 따르지 않음). 한 번 연결에 15초.

- `GET /system/mcp` → `{servers:[서버]}`. 서버: `{name, url, auth:{kind: bearer|oauth|none, set, last4?, expiresAt?(oauth 접근 토큰 만료), needsLogin?(갱신 실패, 다시 로그인)}, enabled, state: ok|error|unchecked, error?, checkedAt?, info?:{serverName, version?}, catalogRevision, tools:[도구], users:{systemAdmins: true, tenants:[t…]}, usedBy:[지침 범위], createdBy, createdAt, revision}`. `users.tenants`가 비면 시스템 관리자만 쓴다.
  - 도구: `{name, title?, description, readOnlyHint, args:[{name, type?, description?, required?}], kind: read|change|notify, coordinator, incident: off|diagnose|notify|propose-approve|propose-auto, tenants:[t…]|"all", new, auto?:{floor, inputs:{arg:{kind: max|incident|template|fixed, value?}}, perIncident, perDay, revert:{tool?|irreversible}, signals?}, hint?}`. 이름이 `[A-Za-z0-9_-]{1,64}`가 아닌 도구는 목록에서 뺀다.
- `POST /system/mcp {name, url, auth:{kind, token?}, users?}` → 201 서버. 이름 `^[a-z][a-z0-9-]{0,30}$`. 먼저 연결해 도구를 읽고, 실패하면 저장하지 않고 422 `mcp-connect`(`error`: "401 Unauthorized", "timeout", "tools/list: …" 같은 한 줄; 응답 본문은 넣지 않음). 같은 이름은 409 `exists`. 처음 도구는 다 꺼진 채(`kind`는 readOnlyHint면 read, 아니면 change)다.
- `PUT /system/mcp/{name} {revision, url?, auth?, users?, enabled?, tools?:{도구: {kind?, coordinator?, incident?, tenants?, auto?, hint?}}}` → 서버. 409 `stale`.
  - `url`·`auth`가 바뀌면 다시 연결해 도구를 다시 읽는다(실패면 바꾸지 않고 422 `mcp-connect`). `auth.kind: bearer`에서 token을 빼면 지금 토큰을 쓴다.
  - 서버가 read-only로 표시하지 않은 도구를 `read`로 두면 422 `kind`. `diagnose`는 read 도구만, `notify`·`propose-*`는 change·notify 도구만(422 `invalid`).
  - `propose-auto`는 하한·모든 인자의 입력 제한·한도(perIncident 1~10, perDay 1~100)·되돌리기(이 서버의 다른 도구 또는 irreversible)가 다 있어야 한다. 되돌릴 수 없으면 하한이 medium 이상이어야 한다. 아니면 422 `auto-incomplete`(`missing`: 빠진 것 목록, 화면과 같은 이름). `inputs.*.kind: incident`의 value는 `id|tenant|app|node|target|signal|title`, template은 `{id}` 같은 자리를 채운다.
  - 도구 설정을 바꾸면 `new`가 꺼진다.
- `POST /system/mcp/{name}/refresh` → 서버. 도구를 다시 읽는다. 있던 도구는 설정을 지키고(read-only 표시가 빠지면 change로, diagnose는 off로), 새 도구는 꺼진 채 `new: true`, 없어진 도구는 뺀다. 바뀌면 `catalogRevision+1`이고 시스템 관리자에게 알림 `mcp-tools-changed`(link `/system/ai/mcp`). 실패하면 `state: error, error`를 남기고 422 `mcp-connect`.
- OAuth(MCP 2025-06-18 인가): `POST /system/mcp {name, url, auth:{kind:"oauth"}, users?}` → 202 `{name, loginUrl, expiresAt}`. 아직 저장하지 않는다. 데몬이 보호 자원 메타데이터(RFC 9728) → 인가 서버 메타데이터(RFC 8414, 없으면 OpenID. `issuer`가 물어본 인가 서버와 다르면 거절) → 동적 클라이언트 등록(RFC 7591, 공개 클라이언트)을 거쳐 PKCE(S256)·`state`·`resource`가 든 인가 주소를 만든다. 모든 주소는 https 공개 주소여야 한다(웹훅과 같은 검사). 등록을 못 하면 422 `mcp-connect`.
  - 돌아올 주소는 `GET /api/v1/system/mcp/oauth/callback`이다. 쿠키(SameSite=Strict)가 따라오지 않으므로 세션 없이 한 번 쓰는 `state`(10분)로만 묶는다. 코드를 토큰으로 바꾸고 연결해 도구를 읽은 뒤 서버를 저장한다. 접근·갱신 토큰과 등록 정보는 봉인 파일 `mcp-oauth-{name}`에만 두고 bbolt·로그·응답에는 없다. 콜백은 "창을 닫아도 됩니다" 한 줄 HTML이다.
  - `GET /system/mcp/{name}/oauth` → `{state: login|connected|failed|expired, error?, server?}`. 진행 중인 로그인이 없고 OAuth 서버면 `connected`와 `server`, 아니면 404.
  - `POST /system/mcp/{name}/oauth/login` → `{name, loginUrl, expiresAt}`(다시 로그인, 끝날 때까지 옛 토큰을 쓴다). OAuth 서버가 아니면 422.
  - 접근 토큰은 끝나기 1분 전부터 쓸 때 갱신 토큰으로 바꾼다. 갱신이 안 되면 `needsLogin: true`이고 호출은 `mcp-connect`로 실패한다.
  - PUT으로 `auth.kind: oauth`는 줄 수 없고(위 경로로), OAuth 서버의 `url`을 바꾸면 422 `login-required`. bearer/none으로 바꾸면 OAuth 토큰을 지운다.
- `DELETE /system/mcp/{name} {confirmName}` → 200 `{trash:{id, expiresAt}}`([지운 것](53-ops-trash.md), 토큰 없이). 이름이 다르면 422 `confirm-name`. 봉인 토큰을 지우고, 지금 지침의 `mcpServers`에서도 뺀다(지난 버전은 그대로).
- `POST /system/mcp/{name}/tools/{tool}/test {incident}` → `{steps:[{label, detail?}], result}`. 지난 사건에 이 도구를 장애 대응이 어떻게 썼을지 보인다(입력 제한으로 채운 인자, 하한, 지금 정책 수준). 도구는 부르지 않는다. 없는 사건은 422 `invalid`.
- URL의 호스트를 바꿀 때 bearer 토큰을 다시 보내지 않으면 422 `token-required`(봉인 토큰은 처음 호스트에만 보낸다).
- 코디네이터: 로그인 사용자가 쓸 수 있는(시스템 관리자, 또는 서버 `users.tenants`와 도구 `tenants`가 함께 허락한 작업 공간의 구성원; 요청마다 sfcd로 확인) `coordinator: true` 도구가 모델에 `mcp_{server}__{tool}`(찾아 쓰는 도구)로 보인다. 도구 줄의 `name`은 `mcp.{server}.{tool}`이다. 서버가 준 설명은 지시가 아닌 데이터로 감싸 넘긴다.
  - read 도구는 바로 부르고 결과는 모델에만 간다(저장하지 않음). 인자는 서버 inputSchema의 이름만, 필수 인자는 있어야 한다(16 KiB까지).
  - change·notify 도구는 제안 카드다: `tool: "mcp.{server}.{tool}"`, `action: "mcp-call"`, `target: "mcp/{server}"`, `mcp: {server, tool}`, `impact`는 change medium·notify low, `revert`는 `auto.revert`의 되돌리기 도구(없으면 "서버가 되돌리는 방법을 알려 주지 않음", irreversible이면 `irreversible: true`·`confirmName`=도구 이름). `PUT /ai/proposals/{id} {payload}`는 같은 인자 규칙으로 고친다.
  - 승인 `POST /ai/proposals/{id}/approve {opId, basisHash}` → `{mcp: {ok, server, tool, error?}}`. 카드를 먼저 approved(op=opId)로 바꾼 뒤 한 번만 부르고, 같은 opId로 다시 보내면 부르지 않고 같은 결과를 준다. 다른 opId는 409 `proposal-approved`. 쓸 수 없게 됐으면 403 `denied`. 결과 원문은 남기지 않고, 다음 차례에 모델에 성공·실패만 알린다. 앞 단계가 MCP 제안이면 그 호출이 성공해야 다음을 승인할 수 있다.
- 장애 대응의 진단: `incident: diagnose`인 read 도구 가운데 그 사건의 작업 공간이 쓸 수 있는 것(클러스터 사건은 전부)을 진단 전에 부른다. 사건의 지침이 `mcpServers`를 고르면 그 서버만 쓴다. 인자는 `auto.inputs`를 사건으로 채운 것이고(필수 인자가 비면 그 도구는 건너뜀), 한 사건에 4번·20초까지, 결과는 한 도구당 2,000자로 잘라 `<mcp-results>`(데이터로만 다룸)로 진단에 넘긴다. 영향 평가에는 넘기지 않는다. 결과는 저장하지 않고, 사건 상세의 `mcpCalls: {server: 횟수}`와 타임라인 `diagnose` 항목의 `inputs`(`mcp.{server}.{tool}`)에 남는다. 지침 시험은 MCP를 부르지 않는다(`mcpCalls: {}`). 진단 프롬프트는 v3.
- 장애 대응의 조치 후보: `incident: propose-approve|propose-auto`인 change·notify 도구 가운데 그 사건의 작업 공간이 쓸 수 있는 것(지침의 `mcpServers`로 좁힘, `auto.signals`가 있으면 그 신호의 사건만)이 규칙 후보 뒤에 붙는다(4개까지). 후보 `action`은 `mcp.{server}.{tool}`, `label`은 도구 title(없으면 이름), `note`는 사건으로 채운 인자 한 줄이다. 필수 인자를 못 채우면 빼고 그 이유를 진단 타임라인에 적는다. 하한은 `auto.floor`(없으면 medium).
  - `propose-approve`는 늘 사람 승인이다. `propose-auto`는 규칙 조치처럼(낮음, 정책 auto-low, 멈춤·조용한 시간·시간당 한도) 자동 대응 계정으로 부르되, 그 도구의 `perIncident`(이 사건)·`perDay`(24시간, 모든 사건) 한도 안에서만이고, 넘으면 승인을 요청한다. 자동 호출이 실패하면 승인을 요청한다.
  - `POST /incidents/{id}/approve {opId, basisHash}`는 MCP 후보면 `{op}` 대신 `{mcp:{ok, server, tool, error?}}`를 준다. 승인부터 기록한 뒤 한 번 부르고(브라우저가 끊겨도 끝까지), 같은 opId 재시도는 기록한 결과를 준다(부르는 중이면 409 `in-progress`). 승인자는 그 MCP 도구를 쓸 수 있어야 한다(아니면 403). 결과 본문은 저장하지 않고 사건의 `mcpCalls`와 타임라인에만 남는다. op가 없으니 사건의 `op`도 없다.
- `propose-*` 도구를 사건 후보로 넣는 것은 다음 단계다.
