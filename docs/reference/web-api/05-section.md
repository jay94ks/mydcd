| `GET /nodes?after=` | `members`, `whoami` | 행: `{id, key, endpoint, systemAddress?, joinID, join, phase, voter, admitsWork, revision, joinRevision, cordoned, cordonedBy?, cordonedAt?, cordonReason?, scheduling?, pendingOperation?, identity?:{operation, phase, failure?, requestedAt?}, identityRotatedAt?, drain?}`. 데몬이 sfcd `members`의 가입 항목(`membership.Entry`)과 수명 주기 행(`NodeLifecycle`)을 서버 ID로 합친다. 가입 중(invited·learner·ready·promoting)이라 수명 주기 행이 없으면 `phase: pending`이고 `scheduling`·`admitsWork`가 없다. `revision`은 수명 주기 행의 revision(격리·복구·제거·신원 교체의 expected, 행이 없으면 가입 항목 것), `joinRevision`은 가입 항목 revision(promote의 expected), `scheduling.revision`은 막기·풀기의 expected. `pendingOperation`은 수명 주기 행의 끝나지 않은 노드 작업. `cordonReason`은 막을 때 적은 사유(sfcd `Scheduling.Reason`, 비우기로 막힌 경우는 없음), `systemAddress`는 서버 고정 주소(`10.254.240.0/20` 안, 클러스터에 더할 때 sfcd가 정함, 모든 망의 터널 주소, `membership.Entry.Address`)다. `identityRotatedAt`은 마지막 신원 교체를 요청한 시각(`identity.requestedAt`과 같음, RFC 3339)이다. 쪽은 8행씩 서버 ID 순. 목록 + `voters, quorum, runtimeRevision, operationEpoch, configurationIndex, ledgerEpoch, ledgerRevision`. `operationEpoch`은 서버 작업(topology) 세대, `ledgerEpoch`은 원장 세대(ModuleEpoch, sfcd가 생략하면 1), `ledgerRevision`은 원장 root revision(whoami `LedgerRootRevision`) |
| `GET /nodes/summary?tenant=&node=&after=` | `node-summary` | `tenant`가 없으면 클러스터 전체(시스템 관리자), 있으면 그 작업 공간 보기 권한으로 허용 서버만. 행: `{node, status, state, ready, stale, role?, cpuPercent?, memUsed?, memTotal?, diskUsed?, diskTotal?, containers, observedAt(Unix 초), observeLimitSeconds, cordonedBy?, cordonedAt?, scheduling, build}`. `build`는 `{enabled, reason?}`: 그 서버에서 이미지 빌드를 돌릴 수 있는지다. 못 돌리면 `reason`이 `ENGINE_BUILD_OFF`(엔진이 빌드를 끔), `WORKLOAD_OFF`(작업 모듈이 꺼짐), `UNKNOWN`(새 관측 보고가 없음) 중 하나다. 빌드 서버를 고르는 화면은 `enabled: false`인 서버를 빼고, 새 보고가 끄라고 한 서버에서는 빌드 시작(`image-build-job-plan`)이 거절된다. `state`는 sfcd 값(ready/unready/unreachable/pending/서버 단계), `status`는 화면 말(unready→degraded, 나머지는 state 그대로). `role`·`cpuPercent`·총량은 클러스터 전체 보기에서만, 작업 공간 보기는 그 작업 공간의 `containers`(와 sfcd가 주면 `memUsed`)만. `clusterApps?`(클러스터 전체 보기, 서버 상세의 "기본 제공 앱" 카드): 그 서버의 node.yaml이 켠 cluster app마다 `{name, image, version?, digest?, ports, state, address?, reason?, restarts, control, actions, runningOn?}`. `image`는 이미지 이름(`sfc/web`), `version`은 그 이미지를 만든 릴리스 버전(예 `0.9.0`, 설치된 이미지의 서명된 릴리스 정보에서 읽는다. 확인하지 못했으면 없음), `ports`는 컨테이너 안에서 듣는 포트 `[{name, port, protocol}]`(sfc-web은 `web` 8080, `acme` 8081, `direct` 8082). `state`는 starting·running·restarting·stopping·exited·failed·image-not-found·image-mismatch·refused(같은 앱을 다른 서버가 이미 돌림: `reason` `already-running`, `runningOn`이 그 서버. 이 서버의 sfcd를 다시 올릴 때까지 그대로)·unknown(서버가 Docker를 읽지 못함), `address`는 시스템 망(sfc-system) 안 컨테이너 주소(도는 서버의 시스템 망 서브넷 `.2`가 web. 클러스터 어디서나 쓰는 주소는 클러스터 공용 주소 `10.254.0.2`), `reason`은 고정 코드(`image-not-installed`: 이미지 패키지 없음, `release-unverified`: 이미지 묶음의 릴리스 정보에 믿는 키의 서명이 없음, `image-digest-mismatch`: 묶음에 릴리스 정보가 적은 이미지가 없거나 깨짐, `image-load-failed`, `reconcile-failed`, `status-unavailable`, `already-running`, `port-unavailable`: node.yaml `port`를 열지 못함, `address-unavailable`: 클러스터 공용 주소를 컨테이너로 넘기지 못함, `seal-key-unreadable`: node.yaml `seal_key_file`을 읽거나 컨테이너용 복사본으로 넘기지 못함(state `failed`). state `starting`에 머무는 동안 시스템 망(sfc-system)에 들어가지 못한 이유: `system-network-pending`: 이 서버의 시스템 망 Bridge가 아직 준비되지 않음(예: 겹치는 Docker 망 때문에 만들지 못함. 원인은 서버의 sfcd 로그 "managed Bridge sources"), `not-work-server`: 작업을 받는 서버가 아님, `no-server-address`: 서버 고정 주소 없음, `no-server-quota`: 서버 전체 한도 없음(클러스터 구성원이 아닌 서버), `server-quota-owner`: 한도가 이 서버의 키 것이 아님, `server-network-limit`: 서버 전체 한도의 망 수를 다 씀, `no-free-system-pool`: 시스템 망에 남은 서버 풀이 없음), `control`은 제어 정책(지금은 `node-config`: node.yaml로만 켜고 끔. 다른 값이 오면 조작 없이 보여 준다), `actions`는 웹에서 할 수 있는 조작(`node-config`는 `[]`). 서버의 관측 보고(SFCP)에서 오므로 `stale`이면 오래된 값이다. 켠 cluster app이 없으면 키가 없다 |
