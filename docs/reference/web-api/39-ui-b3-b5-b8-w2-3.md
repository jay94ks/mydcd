## 장애 자동 대응 (UI-B3~B5·B8, W2.3)

사건·정책은 웹 데이터(bbolt `incidents`, `incident-policy`)이고 실행은 평소의 서명 작업이다. 누가 무엇을 보는지는 요청마다 mydcd에 묻는다: 클러스터 사건·정책은 시스템 관리자, 앱 사건은 그 작업 공간에 역할이 있는 사람(승인·거절·지우기는 관리자).

- 감시기: 30초마다 `/system/automation`의 자동 대응 계정으로 로그인해 `events`를 cursor로 이어 읽는다(시스템 관리자 계정이면 전체, 아니면 읽을 수 있는 작업 공간마다). 클러스터 정책이 `off`면 읽지 않는다. 최근 30분 신호만 센다(처음 켤 때 옛 신호로 사건을 열지 않는다). 앱 신호는 되돌리기 확인용으로 150분(30분 + `windowMinutes` 최대 120분) 보관한다. 끊김 없이 읽기 시작한 때를 cursor 범위마다 기록하고, cursor 만료·감시 꺼짐·로그인 실패 때 지운다. 세션이나 연결이 끊겼을 때는 한 번 다시 로그인해 같은 cursor로 이어 읽는다.
- 규칙: `task-restarted` 같은 Task 10분 안에 3회, `probe-failed` 10분 안에 5회, `task-exited` 10분 안에 2회(앱), `node-unreachable`·`node-resource-low`·`tunnel-down` 1회(클러스터). 같은 대상(앱 하나, 클러스터 신호의 대상 하나)의 열린 사건이 있으면 그 타임라인에 붙는다.
- 후보: `restart-task`(대상 Task), `pause-cd`(지금 버전이 자동 배포로 올라왔을 때만), `cordon-node`, `prune-images`(서버의 안 쓰는 이미지 계획), `reconnect-tunnel`(REQ-54 이벤트의 Tenant·Network와 PairID. 끊김을 본 서버 Node가 `from`, 다른 끝이 `to`. Node가 쌍의 양 끝이 아니면 만들지 않는다. 망마다 사건이 따로 생긴다), `cd-rollback`, `rollback-previous`. 정책에서 `human`이거나 앱이 끈 조치는 빠지고, 만들 수 없는 조치(`move-service`는 옮길 서버를 사람이 골라야 해서 만들지 않음)는 이유와 함께 타임라인에 남는다.
- 되돌리기: 직전 버전(지금 버전보다 앞이고 실패하지 않은 가장 새 버전)의 app.yaml을 `POST /t/{t}/apps/deploy`로 다시 올린다. `cd-rollback`(하한 낮음)은 다음을 코드가 모두 확인할 때만 만든다: 앱 정책 `cdRollback.enabled`이고 `alwaysApprove`가 아님, 지금 버전이 자동 배포(`Kind: cd`), 배포 뒤 `windowMinutes` 안, 두 버전 모두 '데이터 이전' 표시 없음, 차이가 서비스의 이미지·환경 변수(비밀값 참조 제외)·복제본·자원·상태 검사 설정 안, 감시기가 배포 30분 전부터 끊김 없이 읽었고(아니면 '배포 전 신호를 다 보지 못함') 그 앱 신호가 배포 전 30분에는 없었음, 24시간 안에 자동 되돌림 없음. 그러면 되돌리기와 그 앱의 자동 배포 일시 정지를 한 묶음으로 보낸다(일시 정지의 opId는 첫 opId에서 정해져 재시도에도 같다). 첫 op이 `rejected`·`failed`면 일시 정지는 보내지 않는다. 하나라도 어긋나면 `rollback-previous`(하한 보통, 승인)만 남는다. 터널 사건은 클러스터 사건이다(시스템 관리자). 후보가 없으면 `decision.kind: none`(사람에게 넘김).
- AI 판단(진단·영향 평가 역할이 둘 다 쓸 수 있고, 작업 공간이 `excludeTenants`가 아닐 때): 진단(컨텍스트 A, 도구 없음)은 규칙·최근 신호·후보(가린 뒤)를 받아 후보 중에서만 최대 3개를 고르고 순서를 정한다(목록 밖은 버림, 하나도 없으면 사람에게 넘김). 영향 평가(컨텍스트 B, 다른 요청, 도구 없음)는 고른 조치의 정의와 코드가 모은 사실만 받는다. 진단의 문장·신호 원문은 넣지 않는다. 최종 등급 = max(규칙 하한, 평가), 신뢰도가 0.7(진단과 같은 공급자면 0.8) 미만이면 한 단계 올린다. 상세의 `assessment`: `{provider, model, facts, level, reversible, blast, dataRisk, confidence, reasons, floor:{level, reason}, final, policy, fallback, sameProvider}`. 진단·평가가 실패하면(두 모델 모두·형식 오류) 자동 실행하지 않고 승인을 요청한다. 역할이 설정되지 않았으면 규칙만으로 판단한다.
- 결정: 첫 후보의 규칙 최종 등급이 `low`이고, 실제 수준 min(앱, 클러스터; 멈춤이면 `suggest`)이 `auto-low`이며, 정책이 그 조치를 `allow`로 두고, 유지보수 시간이 아니고, 시간당 한도(클러스터 `ratePerHour`, 앱 `ratePerHour`) 안이면 자동 대응 계정으로 바로 보낸다(`X-MyDC-Reason: autofix`, `X-MyDC-Incident: 사건 ID`). `high`면 `rejected`(by `규칙` 또는 `영향 평가`). 나머지는 `pending`(승인 기한 `approvers.deadlineMinutes`, 이유는 `decision.note`)이고 승인할 수 있는 사람(앱: 그 작업 공간 관리자, 클러스터: 시스템 관리자)에게 알림 `incident-approval`(link `/incidents/{id}`). 자동 실행이 거절되면 같은 조치를 승인 요청으로 바꾼다.
- 회복: 실행 10분 뒤 새 신호가 없으면 `recovered`, 이어졌으면 `open`으로 돌리고 같은 조치는 다시 하지 않는다. 기한이 지난 승인 요청은 `expired`.

끝점:

- `GET /incidents?scope&decision&state&tenant&app&q&cursor&limit` → `{items, cursor?, total, pending, level, stopped, watcher:{state: running|stopped|no-automation|login-failed|cursor-expired, at?, error?}}`. `level`은 시스템 관리자에게만(멈춤이면 `off`).
- `GET /incidents/{id}` → 행 + `{title, rule, target, revision, timeline, candidates:[{action, label, note?}], approval?:{title, fields, expiresAt, basisHash, action, target}, op?, guides:{}}`. 볼 수 없는 사건은 404.
- `POST /incidents/{id}/approve {opId, basisHash}` → `{op}`. 승인한 사람 세션으로 서명(`X-MyDC-Reason: incident-approved`). 409 `incident-changed`·`not-pending`, 410 `expired`, 403(관리자 아님). 같은 opId 재시도는 같은 op. mydcd 거부는 그대로 돌려주고 승인 대기로 남는다.
- `POST /incidents/{id}/reject {reason: handled-by-person|wrong-action|not-now|other, note?}` → 204 (`other`면 note 필수, 256자).
- `DELETE /incidents/{id} {confirmName: 사건 ID}` → 204.
- `GET·PUT /incidents/policy`, `POST /incidents/stop`·`/incidents/resume` (시스템 관리자). PUT `{revision, level, ratePerHour(1~30), approvers:{to?, deadlineMinutes(5~240), banner}, quiet(HH:MM-HH:MM 8개까지, 웹 서버 시간), newAppDefault, actions?:{id: allow|approval|human}}`. 하한이 `low`가 아닌 조치를 `allow`로 두면 422 `floor`, 자동 대응 계정 없이 `off` 밖으로 올리면 422 `automation-missing`, 버전이 다르면 409 `stale`.
  - 승인 요청 받는 사람 `approvers.to`: `system-admins`(시스템 관리자만) 또는 `system-and-tenant-admins`(기본, 앱 사건은 그 앱의 작업 공간 관리자도). 모르는 값은 422. `label`은 보내도 무시하고 서버가 사람 수를 넣어 다시 만든다(GET 때마다 mydcd에서 세어 '시스템 관리자 2명 + 그 앱의 작업 공간 관리자'). GET에 `approverOptions:[{to, label}]`. 사람 수를 못 읽으면 수 없이 '시스템 관리자'.
- `GET·PUT /t/{t}/apps/{app}/incident` (읽기: 구성원, 바꾸기: 관리자). 앱 `level`은 클러스터보다 높게 저장해도 되고 실제 동작은 min(앱, 클러스터)이다. `ratePerHour` 1~10, `cdRollback.windowMinutes` 5~120, `actions`는 `available`의 id만.
- 코디네이터로 열기: `POST /ai/conversations {incident}` → 그 사건 제목·작업 공간·칩 `{kind: incident, id}`로 새 대화(볼 수 없는 사건은 404). 코디네이터 읽기 도구 `incidents_list`·`incidents_get`. 제외한 작업 공간의 사건 하나(객체 결과의 문자열 필드가 그 이름)는 통째로 "보내지 않음"이 된다.
- `GET /t/{t}/apps/{app}/incident/versions` → `{items:[{version, summary, by, cd, at, migration, auto?}]}`, `PUT …/versions/{v} {migration}` (관리자). `auto`는 직전 버전보다 `volumes`·`networks`·`secrets`·`domains`·`ingress`·`lifecycle`(상태 검사 스크립트)을 바꾼 곳(경로, 최근 20개 버전만)이다. `healthcheck` 설정은 가벼운 변경이라 들지 않는다.
