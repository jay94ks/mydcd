## 이미지 빌드 (mydcd 실제 계약)

캔버스 ImageBuilds(목록, 로그), ImageBuildNew(새 빌드, Dockerfile, 파일 트리), ImageBuildCache(캐시 비우기)에 쓴다. 데몬은 그 사람 세션으로 mydcd의 `image-builds`(Part policy·contexts·versions·jobs·caches·cache-prunes), `build-context-content`, `image-build-logs`, `image-build-cache`를 읽고, 바꿀 때는 실제 action(`set-image-build-policy`·`put-build-context`·`delete-build-context`·`delete-build-version`·`begin-image-build`·`cancel-image-build`·`delete-image-build-job`·`prune-build-cache`)에 서명해 보낸다. 권한, 정책 범위, 기록 CAS는 mydcd가 판단한다. 데몬은 행 모양만 바꾼다(32바이트 id 옆에 버전 번호, 정책 펼치기). 32바이트 값은 hex, 시각은 RFC 3339다. 모든 변경은 `{op}`를 돌려준다.

직접 작성 초안(kind `draft`)은 mydcd `build-draft`로 고친다. 데몬이 요청마다 초안 범위를 열고(plan), 편집 증명은 세션 키로 데몬이 서명한다(브라우저는 관여하지 않는다). 파일 내용은 지나가기만 하고 웹 bbolt에 남지 않는다.

빌드 비밀값은 같은 작업 공간 보관함의 키를 가리키는 마운트(`secrets[{id, realm, secret, key}]`)일 뿐이고 값은 지나가지 않는다. 비밀 빌드 인자는 없다.

- `GET /t/{t}/build-policy` → `{exists, revision, nodes:[{node, root:{id, generation, path}}], concurrency, seconds, cpuMillis, memoryBytes, workspaceBytes, cacheBytes, registry, platforms, builderImage, cleanup:{highWaterPercent, unusedDays}, limits:{zipBytes, expandedBytes, fileReadBytes, logPageBytes}}`. 정책이 없으면 `exists:false`. `workspaceBytes`는 입력 수락 예산, `cacheBytes`는 상한이 아니라 정리 목표다.
- `PUT /t/{t}/build-policy` `{opId, policy:{nodes:[{node, root}], concurrency, seconds, cpuMillis, memoryBytes, workspaceBytes, cacheBytes, registry, platforms, builderImage?, cleanup:{highWaterPercent, unusedDays}}, expected?}` → `set-image-build-policy`. `root`는 저장 경로 id다. 지금 정책에 있는 서버·경로는 그대로 쓰고, 새 경로는 `GET /t/{t}/storage` 행의 `root`(REQ-58, mydcd가 채우는 전체 참조)를 쓴다. 그 작업 공간 경로가 아니면 422 `root-unknown`. 새 경로는 `allowed`이고 꺼내는 중(`draining`)이 아니어야 한다. `builderImage`를 안 보내면 지금 것을 쓰고, `name:tag`이면 데몬이 `image-resolve`의 `Pinned`(`authority/repository@digest`)로 바꾼다(신뢰되지 않거나 못 풀면 422 `builder-digest`). 범위를 벗어나면 422 `invalid`.
- `GET /t/{t}/build-contexts?after=` → 행: `id`, `kind`(`upload`/`git`/`draft`), `revision`, `node`, `root`, `dockerfile`, `args{}`, `secrets[]`, `repository`, `tags`, `platforms`, `git?{repository, ref, path, credentialProfile, automatic}`, `gitCheck?{code, commit?, at?, entries}`, `version`(가장 새 보존 버전 번호, 0이면 없음), `versions[{number, id, bytes, expandedBytes, entries, at?, commit?}]`(새 것부터), `lastBuild?`(아래 빌드 행).
- `PUT /t/{t}/build-contexts/{id}` `{opId, context:{kind, node, dockerfile, args?, secrets?, repository, tags, platforms, git?}, expected?}` → `put-build-context`. node는 빌드 정책의 서버 중 하나이고(아니면 422 `node-not-in-policy`), 저장 경로는 정책의 그 서버 경로다. 정책이 없으면 409 `no-policy`. 저장한 뒤 kind·서버를 바꾸면 mydcd가 op를 거절한다(`failed`).
- `POST /t/{t}/build-contexts/{id}/delete` `{opId, expected?}` → `delete-build-context`. 보존 버전이 남아 있으면 mydcd가 거절하므로 데몬이 먼저 409 `versions-left`(메시지에 번호)로 답한다. 없는 ID는 404.
- `POST /t/{t}/build-contexts/{id}/versions/{version}/delete` `{opId}` → `delete-build-version`(Expected = 버전 번호). 쓰이고 있는 버전은 op가 거절된다. 번호가 아니면 422, 없는 버전은 404.
- `GET /t/{t}/build-contexts/{id}/tree?version=N` → `{version, id, tree, entries:[{path, directory, executable, bytes, digest}], dockerfile}`. 없는 버전은 404. version 0이나 없음은 초안: `{version: 0, revision, digest?, initialized, entries, dockerfile}`. `revision`은 초안 편집의 `expected`다. 새 draft 컨텍스트는 `initialized:false`, `revision:1`이다. 초안 읽기와 편집은 관리 권한이 필요하다.
- `GET /t/{t}/build-contexts/{id}/file?version=N&path=` → 파일 내용 그대로(REQ-57, `application/octet-stream`, `Content-Security-Policy: sandbox`, no-store, 실행 파일이면 `X-MyDC-Executable: 1`). `limits.fileReadBytes`보다 크면 413. version 0은 지금 초안의 파일이다(`build-draft` Kind `file`, 그 사이 초안이 바뀌면 409 `conflict`). 보존 버전은 `build-context-content` Part `file`로 24 KiB씩 읽는다.
- `POST /t/{t}/build-contexts/{id}/verify` → `check-build-context` 결과 `{context, code(OK/SOURCE_FETCH/UNTRUSTED_BASE/INVALID_CONTEXT), commit, tree, entries, baseSources, expandedBytes, …}`. Git만. op가 아니다.
- `POST /t/{t}/build-contexts/{id}/build` `{opId, build?, version?}` → `image-build-job-plan` 뒤 `begin-image-build`. version은 보존 버전 번호(기본 가장 새 것), 없으면 409 `no-version`. build는 빌드 ID(기본 `build-<opId>`). 계획 뒤 컨텍스트·정책이 바뀌었거나 범위를 넘으면 op가 거절된다.
  - 빌드 Secret 묶음 승인(CLI `build run`과 같음): 컨텍스트 `secrets`가 승인이 필요한 묶음의 Secret을 쓰면, 데몬이 `begin-image-build` 원본에 한 번 서명해 웹 bbolt에 **보내지 않고** 둔다. 그 원본을 Origin으로 컨텍스트 secrets의 realm마다 `vault-approval-plan`(ID `compose/<request ID>`)을 묻는다. 승인이 남아 있으면 op는 202, `state:"running"`, `errorCode:"approval-required"`, `approvals:[{realm, group, services, state}]`이다. `GET /t/{t}/vault/approvals`에도 `kind:"build"`, `context`, `build`와 함께 나온다. 모두 승인되면 같은 원본을 보낸다. 승인이 필요 없으면 바로 보낸다. 기다리는 op에 `resume`을 보내면 409 `approval-required`. 승인을 모두 받은 뒤 mydcd가 원본을 거절하면(승인은 한 시각에 함께 유효해야 해서, 늦은 승인 때문에 앞 승인이 `MaxApprovalAge`를 넘긴 경우 등) op는 `failed`, `errorCode:"approval-rejected"`다. 그 원본의 결과는 바뀌지 않으므로 새 opId로 빌드를 다시 시작한다. 응답을 모르면(`unknown`) 같은 원본을 `resume`한다.
  - `POST /t/{t}/build-approvals/{opId}/approve` `{realm?(기본 작업 공간), group, password}` → 비밀번호를 SecretInput(mode approve)으로 그 묶음의 승인 서버에 보내고, 남은 승인이 없으면 원본을 보낸다 → `{op}`. 응답은 배포 승인과 같다(403 `approval-denied`, 502 `approval-unknown`, 409 `not-required`·`already-approved`). **비밀번호는 어디에도 남기지 않는다.**
- `GET /t/{t}/builds?context=&after=` → 최신 순. 행: `id`, `context`, `node`, `user`, `phase`(queued/running/unknown/succeeded/failed/cancelled), `version`(번호), `versionId`, `number`, `revision`, `createdAt?`, `closedAt?`, `cancel?`, `result?{code, image, bytes}`, `automatic?`. `unknown`은 결과를 아직 모름이다.
- `GET /t/{t}/builds/{id}/log?after=|tail=1` → 바이트 한 쪽(24 KiB) `{text, offset, next, total, available, truncated, gap, unclosed, phase, done}`. 다음 쪽은 `after=next`. 쪽 경계가 줄 중간일 수 있어 줄 나누기는 화면이 한다. `truncated`는 로그가 8 MiB 상한에 닿아 **끝이** 잘림(그 뒤 출력은 남지 않는다), `gap`은 빈 구간, `unclosed`는 쓰기 흐름이 닫혔다는 기록이 아직 없음이다. `unclosed`는 빌드가 살아 있다는 증거가 아니다(실행 여부는 `phase`로 본다). `done`은 다 읽음. `?tail=1`이면 마지막 한 쪽(`offset` = max(0, total−24 KiB))을 돌려주고, 그 `next`로 새로 붙은 출력을 이어 읽는다(REQ-59, `after`와 함께 쓰면 422).
- `POST /t/{t}/builds/{id}/cancel` · `POST /t/{t}/builds/{id}/delete` `{opId}` → `cancel-image-build`(끝나지 않은 빌드) · `delete-image-build-job`(끝난 빌드, 로그도 지워진다). Expected = 빌드 revision. 없는 빌드는 404.
- 캐시:
  - `GET /t/{t}/build-cache` → `{cacheBytes, cleanup, nodes:[{node, reportedBytes, entries, scopes}], caches:[{cache, node, context, root, builder, job, contextDeleted?, code?, usage?{recorded, available, borrowed?, observedAt?, lastAttemptAt?, lastAttemptCode?, observedKind?, reportedBytes, count, kinds:[{kind, count, inUse, reportedBytes, sharedBytes}], cleanup?{job, steps:[{kind, selected, maxUsedSpace, sentAt?, returnedAt?, code?, removedCount, reportedBytes}]}}}], cleaning:[{id, node, context, cache, user, filter, state(queued/running/succeeded/failed), code?, acceptedAt?, closedAt?, removedCount?, reportedBytes?, automatic?}]}`. `observedKind`는 그 관측을 한 쪽이다(없음 = 빌드 뒤, `cache-prune` = 정리 뒤). cleaning `state`에는 `unknown`(결과를 아직 모름)도 있다. `code`는 끝난 행에만 있다(`OK`, 실패면 `FAILED`·`PERMISSION_REVOKED`·`TIMEOUT`). queued·running·unknown에는 code가 없고, mydcd는 기다리는 이유를 주지 않는다.
  - `GET /t/{t}/build-cache/entries?node=&cache=&after=` → 캐시 범위 하나의 항목 한 쪽 `{available, borrowed?, observedAt?, lastAttemptAt?, lastAttemptCode?, reportedBytes, count, offset, next, entries:[{id, kind, bytes, createdAt?, lastUsedAt?, uses, inUse, mutable, shared}], cleanup?}`. 다음 쪽은 `after=next`. 시각은 모두 RFC 3339.
  - `POST /t/{t}/build-cache/prune` `{opId, node, cache, filter:{mode: all|unused|entries, ids?, unusedDays?}}` → `prune-build-cache`. 수락은 끝이 아니다. 진행은 `cleaning`에서 본다. 자동 정리 설정은 정책의 `cleanup`이다(`PUT /build-cache/policy`는 없앴다).
- zip 올리기(REQ-47, upload 종류): 바이트는 submit에 실리지 않는다. 데몬이 32 KiB 조각(begin의 `ChunkBytes`=32768; 예전에 24 KiB로 연 upload는 24 KiB 그대로)마다 세션 키로 서명한 Record 조각(`Record:true`)을 `build-zip-transfer`로 보낸다. 소유 서버가 그 조각을 바로 확정하고(`Recorded`), 돌려준 `UploadRevision`을 다음 조각의 CAS로 쓴다. 조각마다 작업(op)을 만들지 않으므로 500 MB zip도 사용자 작업 기록 한도(256개)에 걸리지 않는다. 작업은 begin과 `upload-build-zip` 둘뿐이다. stage만 하는 서버면 예전처럼 영수증을 `put-build-zip-part`로 기록한다. 끝낼 때는 봉인 영수증을 받아 `upload-build-zip`으로 새 버전을 만든다. zip 내용은 지나가기만 하고 웹 bbolt에 남지 않는다. 열린 upload는 작업 공간당 16개, 24시간까지이고 정책 `cacheBytes` 안이어야 한다(넘으면 mydcd가 begin을 거절한다).
  - `PUT /t/{t}/build-contexts/{id}/zip?opId=`: 본문이 zip 원본이다(`Content-Type: application/zip`, 8 MiB까지, 크면 413). 데몬이 upload `web-<opId>`를 열고 조각과 봉인을 바로 보낸 뒤 `upload-build-zip` op 하나를 돌려준다. 같은 opId로 다시 보내면 같은 upload를 이어 간다. 그래서 begin도 조각처럼 웹 bbolt에 서명 원본을 남기지 않는다(답을 잃으면 upload를 다시 읽어 정한다. mydcd는 같은 upload ID를 두 번 열지 않는다). 열지 못하면 409 `upload-refused`. `expected`는 더 쓰지 않는다(보내도 무시).
  - `POST /t/{t}/build-contexts/{id}/zip-uploads` `{opId, length, digest}` → `begin-build-zip-upload`. digest는 zip 전체의 sha256 hex(0은 422), upload ID는 `web-<opId>`. upload 종류가 아니면 409 `not-upload`.
  - `GET …/zip-uploads/{upload}` → `{upload, context, length, digest, revision, expiresAt, partBytes, chunkBytes, chunks, missingChunks, complete}`. 끝났거나 취소된 upload, 남의 upload는 404.
  - `PUT …/zip-uploads/{upload}/chunks/{n}`: 본문이 n번째 조각(정확히 `chunkBytes` 바이트, 마지막만 나머지. 새 upload는 4 MiB = 128 × 32 KiB, 예전 24 KiB upload는 4,177,920바이트). 데몬이 `partBytes` 조각으로 나눠 빠진 것만 보낸다. 마지막 조각에서 zip 전체 digest가 다르면 422 `part-refused`. 그 사이 컨텍스트·정책이 바뀌었거나 기한이 지났거나 upload revision이 움직였으면 409 `conflict`. 데몬은 다른 revision으로 자동 재시도하지 않으니, 같은 조각을 다시 보낸다(이미 확정된 조각은 건너뛴다). 저장 경로를 못 쓰면 503 `storage-unavailable`. 조각 op는 bbolt에 남기지 않는다.
  - `POST …/zip-uploads/{upload}/finish` `{opId}` → 데몬이 봉인을 받고(mydcd가 zip 경로·Dockerfile·풀린 크기를 검사, 아니면 422 `part-refused`) `upload-build-zip`, 새 버전. 빠진 조각이 있으면 409 `incomplete`.
  - `DELETE …/zip-uploads/{upload}` `{opId}` → `abort-build-zip-upload`.
- 직접 작성 초안(kind `draft`, `build-draft`):
  - `PUT /t/{t}/build-contexts/{id}/files` `{opId, path, text? | data?(base64), executable?, expected?}` (넣기) · `DELETE …/files` `{opId, path, expected?}` (지우기, 폴더면 그 아래 전부) · `POST …/files/move` `{opId, path, to, expected?}` (옮기기) → `{code: "OK", revision}`. op가 아니라 바로 끝나는 호출이고 `/ops`에 남지 않는다. 같은 opId로 다시 보내면 같은 편집으로 취급된다(편집 ID `e-<opId>`). expected는 초안 tree의 `revision`(없으면 지금 값)이고, 맞지 않거나 그 사이 컨텍스트·정책이 바뀌면 409 `conflict`(tree를 다시 읽는다). 파일 하나는 1 MiB까지이고 24 KiB보다 크면 데몬이 조각으로 보낸다. 경로는 정리된 상대 경로(`../`·절대 경로는 422).
  - `POST /t/{t}/build-contexts/{id}/commit` `{opId, expected?}` → 초안을 얼린 뒤 `publish-build-draft`(Expected = 초안 revision) → `{op}`, 새 버전. 빈 초안은 409 `empty-draft`, expected가 지금 초안과 다르면 409 `conflict`.
