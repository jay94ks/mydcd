## 컨테이너 상세·이력·로그와 옮기기 전 검사

컨테이너는 `/observe`와 같은 방식으로 고른다. 앱 Task는 `/t/{t}/apps/{app}/task?service=&instance=`, 단독 컨테이너는 `/t/{t}/standalone/{name}/task`다. 서버 읽기, 비밀값 가림, 권한은 mydcd가 맡는다. 읽기는 작업 공간 Read 권한이면 된다. 시각은 Unix 초다.

- `GET …/task` → 적용된 실행 설정과 drift: `{selection, node, name, nativeID, image, digest, command?, entrypoint?, workingDir?, user?, readOnly, capAdd?, privileged, cpus?, memoryBytes?, logDriver, logOptions?, env:[{key, value? | secret?}], mounts, networks, ports?, stopSignal, stopGrace, generation, drift?, observedAt}`. 보관함에서 오는 환경 변수는 `secret`(`secret:<object>/<key>`)만 보이고 값은 없다. `drift`는 목표와 다르게 적용된 app.yaml 경로다(예: `services.web.image`). `ports`는 `[{port, protocol, ingress?, published?:[{hostIp?, hostPort}]}]`이고(hostPort는 Docker처럼 문자열, 예: `"18080"`), `published`는 서버에 실제로 잡힌 호스트 바인딩이다(mydcd `container-detail`의 Docker inspect 값을 포트·프로토콜별로 묶음, Docker가 고른 포트도 실제 값). 없으면 그 포트는 망 안에서만 열려 있다.
- `GET …/task/history?limit=`(0..200, 0이면 20) → `{exits:[{at, reason(exit/oom/health/node-restart/user/log-clear), exitCode, generation, nativeID}], checks:[{checker, consecutiveFailures, results:[{at, ok, durationMs, message?}]}]}`. 최신 순이다.
- `GET …/task/logs?cursor=&limit=`(0..5000) → `{lines:[{seq, …로그 줄}], cursor?, masked}`. cursor보다 오래된 줄을 오래된 순으로 준다(cursor가 없으면 최신 줄부터). 응답의 cursor로 더 뒤를 빠짐없이 읽고, cursor가 없으면 끝이다. 줄에 찍힌 비밀값은 `«가림: object/key»`로 바뀌어 오고, `masked`는 그런 줄의 수다. 실시간 따라가기는 컨테이너 스트림(`/stream?kind=logs`)을 쓴다.
- `GET …/task/stats` → `{items:[{at, …stats}]}`: 최근 1시간 동안 30초 간격 표본이다.
- `POST /t/{t}/apps/{app}/task/restart` `{opId, service, instance, operation?}` → `{op}` (`restart-task`). 데몬이 mydcd `task-restart-plan`을 읽어 `control.TaskRestartChange`에 계획의 `Target`(지금 도는 그 컨테이너에 고정)을 넣고 `Expected` = 계획의 `InventoryRevision`으로 서명한다(CLI와 같다). 그사이 컨테이너가 바뀌었으면 op가 ConditionFailed다. `expected`는 더 쓰지 않는다(보내도 무시). 그 Task 하나만 다시 시작한다. 결과는 app operation `operation`(기본 `restart-<opId>`, 소문자로 시작하는 lifecycle ID)으로 본다. 관리 권한이 필요하고, 없는 앱·Task는 404다.
- `GET /t/{t}/apps/{app}/relocation-check?service=&node=` → `{from, to, ok, checks:[{name, ok, detail?}], volumes:[{name, kind, node, step}], steps}`. 배치 탭의 '옮기기 전 검사'다. mydc-web이 실행 중인 버전에서 그 서비스의 `x-mydc.node`를 바꾸고(앱 소유의 노드 고정 데이터 저장소가 있으면 그 `x-mydc.node`도) mydcd에 계획을 맡긴다. 판단은 mydcd가 한다. checks는 `plan` 하나다. 거절되면 `ok: false`이고 `detail`에 mydcd의 입력 오류 코드와 내용이 들어간다. 계획 권한이 없으면 계획처럼 403이다. 실행 중인 버전에 없는 서비스는 404, 여러 서버에 도는 서비스(`x-mydc.nodes`)는 422다. 한 번에 데이터 저장소 하나만 옮길 수 있어 둘 이상이면 `plan`이 실패한다. steps는 보낼 순서다. `app`은 `x-mydc.node`만 바꾼 새 버전을 올리는 것이고, `volume-move`는 그 버전을 실은 데이터 저장소 옮기기(UI-64)다. volume의 step이 `not-movable`이면(다른 서버에 고정된, 이 앱 소유가 아닌 저장소) 옮길 수 없다.
- 로그 정리(UI-3C, `mydc app clear-logs`와 같다, mydcd에 있음):
  - `GET /t/{t}/apps/{app}/logs-clear/plan?service=&instance=` → `{clearable, driver, reason?, service, instance?, node?, target?, inventoryRevision?, targets:[{key, service, instance?, kind, node, nativeID, startedAt, logDriver, generation, retained?, reason}]}`. targets는 다시 만들 컨테이너이고, reason은 `target`(고른 컨테이너)이나 `depends-on`(그것에 기대는 서비스)이다. 로그 방식이 local·json-file이 아니면 `clearable: false`, `reason: unsupported-log-driver`, `driver`에 그 방식이 오고 targets는 비어 있다. 작업 공간 Deploy 권한이 필요하다(mydcd가 판단, 아니면 403).
  - `POST /t/{t}/apps/{app}/logs-clear` `{opId, service, instance?, target}` → `{op}` (`clear-app-logs`, operation `logs-clear-<opId>`). `target`은 보여 준 계획의 target이다. 그새 대상이 바뀌었으면 409 `plan-changed`(계획을 다시 읽는다), 정리할 수 없는 로그 방식은 409 `unsupported-log-driver`. Expected는 데몬이 계획의 inventoryRevision으로 채운다(앱 revision이 아니다).
  - `GET /t/{t}/apps/{app}/logs-clear/{opId}` → `{operation, phase(Retiring/Removed/Recreating/Succeeded), target, oldContainers, newContainers}`. 행 모양은 targets와 같다(reason 없음). 실패는 op 결과와 앱 operation(`logs-clear-<opId>`)으로 본다.
  - 다시 만든 컨테이너는 쓰기 계층과 로컬 로그를 잃고, 데이터 저장소와 외부 로그 사본은 남는다. 단독 컨테이너는 대상이 아니다.
- 복제본: app.yaml `services.<svc>.x-mydc.nodes: [..]`. 배포 계획(`/plan` 스트림)의 서비스 행에 `nodes`가 더 붙는다. 다른 끝점은 바뀌지 않는다.
