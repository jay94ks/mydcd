## 컨테이너 상세·이력·로그와 옮기기 전 검사

컨테이너는 `/observe`와 같은 방식으로 고른다. 앱 Task는 `/t/{t}/apps/{app}/task?service=&instance=`, 단독 컨테이너는 `/t/{t}/standalone/{name}/task`다. 서버 읽기, 비밀값 가림, 권한은 sfcd가 맡는다. 읽기는 작업 공간 Read 권한이면 된다. 시각은 Unix 초다.

- `GET …/task` → 적용된 실행 설정과 drift: `{selection, node, name, nativeID, image, digest, command?, entrypoint?, workingDir?, user?, readOnly, capAdd?, privileged, cpus?, memoryBytes?, logDriver, logOptions?, env:[{key, value? | secret?}], mounts, networks, ports?, stopSignal, stopGrace, generation, drift?, observedAt}`. 보관함에서 오는 환경 변수는 `secret`(`secret:<object>/<key>`)만 보이고 값은 없다. `drift`는 목표와 다르게 적용된 app.yaml 경로다(예: `services.web.image`). `ports`는 `[{port, protocol, ingress?, published?:[{hostIp?, hostPort}]}]`이고(hostPort는 Docker처럼 문자열, 예: `"18080"`), `published`는 서버에 실제로 잡힌 호스트 바인딩이다(sfcd `container-detail`의 Docker inspect 값을 포트·프로토콜별로 묶음, Docker가 고른 포트도 실제 값). 없으면 그 포트는 망 안에서만 열려 있다.
- `GET …/task/history?limit=`(0..200, 0이면 20) → `{exits:[{at, reason(exit/oom/health/node-restart/user/log-clear), exitCode, generation, nativeID}], checks:[{checker, consecutiveFailures, results:[{at, ok, durationMs, message?}]}]}`. 최신 순이다.
- `GET …/task/logs?cursor=&limit=`(0..5000) → `{lines:[{seq, …로그 줄}], cursor?, masked}`. cursor보다 오래된 줄을 오래된 순으로 준다(cursor가 없으면 최신 줄부터). 응답의 cursor로 더 뒤를 빠짐없이 읽고, cursor가 없으면 끝이다. 줄에 찍힌 비밀값은 `«가림: object/key»`로 바뀌어 오고, `masked`는 그런 줄의 수다. 실시간 따라가기는 컨테이너 스트림(`/stream?kind=logs`)을 쓴다.
- `GET …/task/stats` → `{items:[{at, …stats}]}`: 최근 1시간 동안 30초 간격 표본이다.
- `POST /t/{t}/apps/{app}/task/restart` `{opId, service, instance, operation?}` → `{op}` (`restart-task`). 데몬이 sfcd `task-restart-plan`을 읽어 `control.TaskRestartChange`에 계획의 `Target`(지금 도는 그 컨테이너에 고정)을 넣고 `Expected` = 계획의 `InventoryRevision`으로 서명한다(CLI와 같다). 그사이 컨테이너가 바뀌었으면 op가 ConditionFailed다. `expected`는 더 쓰지 않는다(보내도 무시). 그 Task 하나만 다시 시작한다. 결과는 app operation `operation`(기본 `restart-<opId>`, 소문자로 시작하는 lifecycle ID)으로 본다. 관리 권한이 필요하고, 없는 앱·Task는 404다.
- `GET /t/{t}/apps/{app}/relocation-check?service=&node=` → `{from, to, ok, checks:[{name, ok, detail?}], volumes:[{name, kind, node, step}], steps}`. 배치 탭의 '옮기기 전 검사'다. sfc-web이 실행 중인 버전에서 그 서비스의 `x-sfc.node`를 바꾸고(앱 소유의 노드 고정 데이터 저장소가 있으면 그 `x-sfc.node`도) sfcd에 계획을 맡긴다. 판단은 sfcd가 한다. checks는 `plan` 하나다. 거절되면 `ok: false`이고 `detail`에 sfcd의 입력 오류 코드와 내용이 들어간다. 계획 권한이 없으면 계획처럼 403이다. 실행 중인 버전에 없는 서비스는 404, 여러 서버에 도는 서비스(`x-sfc.nodes`)는 422다. 한 번에 데이터 저장소 하나만 옮길 수 있어 둘 이상이면 `plan`이 실패한다. steps는 보낼 순서다. `app`은 `x-sfc.node`만 바꾼 새 버전을 올리는 것이고, `volume-move`는 그 버전을 실은 데이터 저장소 옮기기(UI-64)다. volume의 step이 `not-movable`이면(다른 서버에 고정된, 이 앱 소유가 아닌 저장소) 옮길 수 없다.
- 로그 정리(UI-3C, 설계): 로그는 서버마다 sfcd 로그 보관소에 있다. 지우기는 모든 멤버 서버에 보내는 바로 요청이고, 컨테이너는 건드리지 않는다. 서명한 변경이 아니어서 opId가 없고 op로 남지 않는다. 같은 요청을 다시 보내도 결과가 같다.
  - `POST /t/{t}/logs/clear` `{app | standalone, service?, key?}` → `{nodes:[{node, code, containers, removed}], cleared, total}`. `service`를 비우면 앱 전체, `key`는 작업 키 하나(`workload/task/...`)다. 단독 컨테이너에는 `service`·`key`를 쓰지 않는다. `code`는 `ok`·`denied`·`unreachable`·`unavailable`이고, 서버마다 그 작업 공간의 Deploy 권한을 자기가 확인한다. `cleared`는 `ok`인 서버 수, `total`은 답한 서버 수다. `ok`가 아닌 서버는 로그를 그대로 두므로, 화면은 "N대 중 M대 지움"과 다시 보내기를 보여 준다. 지운 서버의 이벤트 기록에 `container-logs-cleared`(누가, 지운 줄 수)가 남는다.
  - `GET /t/{t}/logs/stored?app=|standalone=&service=&key=&node=` → `{nodes:[{node, code, logs:[{container, name, service, key, lines, size}]}]}`. 보관소가 지금 지닌 로그 목록이며, 지워진 컨테이너의 것도 들어간다. 줄 내용은 주지 않는다(비밀값은 읽을 때 살아 있는 컨테이너의 입력으로 가린다). `node`를 주면 그 서버만 묻고, 모르는 서버는 404다. 작업 공간 Read 권한이면 된다.
  - 잘못된 선택(앱과 단독 둘 다, 둘 다 없음)은 400이다.
- 복제본: app.yaml `services.<svc>.x-sfc.nodes: [..]`. 배포 계획(`/plan` 스트림)의 서비스 행에 `nodes`가 더 붙는다. 다른 끝점은 바뀌지 않는다.
