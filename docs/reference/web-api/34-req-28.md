## 데이터 저장소 파일

웹 자동 백업 같은 곳에서 데이터 저장소 안 파일을 다룬다([volume-files.md](../volume-files.md)). 목록·읽기·쓰기·지우기는 모두 그 사람의 서명된 op다: 데몬이 `volume-file-plan`으로 바꿀 내용을 받아 `Expected` = 계획의 revision으로 서명하고, 원본을 저장한 뒤 보낸다(작업이 예약됨). 그다음 본문을 purpose18 스트림으로 한 번 주고받는다. op에는 경로·길이·digest만 들어가고 내용은 웹 bbolt와 작업 기록에 남지 않는다. 경로·용량 검사와 권한(작업 공간 관리자, 또는 경로 위임을 받은 계정)은 sfcd가 맡는다. 경로는 `/`로 시작하지 않는 상대 경로다.

응답을 잃으면 파일이 거기 있다는 이유로 성공이라고 보지 않는다. 그 작업을 `volume-file-status`로 읽어, 예약 상태면 같은 op로 다시 스트림하고, 끝났으면 저장된 응답을 받는다. 그래도 모르면 502 `volume-file-unknown`이고, 같은 opId로 다시 보내면 새로 서명하지 않고 그 op를 이어 간다. 읽기는 길이·digest·EOF가 응답의 결과와 맞을 때만 내보낸다(아니면 502 `volume-file-mismatch`). 끝난 읽기의 바이트를 잃으면 새 op로 한 번 더 읽는다.

- `GET /t/{t}/volumes/{name}/files?prefix=&after=` → `{items:[{path, bytes, modifiedAt}], next}`. 한 쪽은 64개(`volume-file-list` op 하나)이고 `next`를 다음 `after`로 보낸다. digest는 더 오지 않는다.
- `GET /t/{t}/volumes/{name}/file?path=` → 파일 내용 그대로(attachment, `Content-Security-Policy: sandbox`, no-store, 64 MiB까지). `X-SFC-Digest: sha256:<hex>`. 없는 파일 404, 상한을 넘으면 413.
- `PUT /t/{t}/volumes/{name}/file?path=&opId=&overwrite=1`: 본문이 파일 내용이다(웹으로는 64 MiB까지, 넘으면 413). → `{op, file:{path, bytes, digest}}` (`volume-file-put`). 이미 있는데 overwrite가 없으면 409 `exists`. 같은 opId·같은 내용은 그 op를 이어 가고, 다른 내용이면 409 `op-conflict`.
- `DELETE /t/{t}/volumes/{name}/file` `{opId, path}` → `{op, file:{path}}` (`volume-file-delete`). 없는 파일 404.
- `POST /t/{t}/volumes/{name}/file-grants` `{opId, prefix, user}` → `{op}` (`volume-file-grant`). `DELETE`에 같은 본문을 보내면 `volume-file-revoke`다. prefix는 `/`로 끝나는 폴더이고, user는 계정의 user ID(자동 작업 계정)다. 위임받은 계정은 그 저장소의 그 경로 아래에서만 목록·읽기·쓰기·지우기를 할 수 있다. 위임은 작업 공간 관리자만 하고, 받는 계정은 그 작업 공간의 구성원(보기 이상)이어야 한다(아니면 op가 forbidden). payload는 `access.VolumeFileFolderGrant`이고 `Expected`는 구성원 목록 조회의 catalog revision(`TenantMembersRevision`, 작업 공간 revision이 아님)이다. 같은 위임을 다시 주면 applied, 없는 위임을 회수하면 invalid.
