## 장애 대응 (REQ-9·11 mock)

- 자동 대응 계정 범위(시스템 관리자, 본인은 읽기만):
  - `GET /users/{u}/scope` → `{user, actions, keyOnly, revision}`. mydcd 계정 기록의 `Operations`·`AutomationOnly`를 읽는다. `actions`가 비면 제한 없음. revision은 계정 revision이다. u는 사용자 ID다.
  - `PUT /users/{u}/scope` `{opId, actions, keyOnly, expected?}` → `set-account-scope {User, Operations, KeyOnly}`(Expected 기본 = 계정 revision, 계정 세션이 모두 끝난다). 이 계정의 op는 `actions` 안 action만 된다(역할 권한과 함께). `keyOnly`면 비밀번호·토큰 로그인이 안 된다. 둘 다 비우면 범위를 지운다. 계정 공개키 등록·끄기는 지금처럼 `put-user`(`POST /ops`)다.
- 서버 새 배치 제외(시스템 관리자): `POST /nodes/{node}/cordon` `{opId, reason?(256자 이하 한 줄), expected?}` → `cordon-node`(`control.NodeCordonChange{ID, Reason?}`), `POST /nodes/{node}/uncordon` `{opId, expected?}` → `uncordon-node`. expected 기본값은 그 서버 `scheduling.revision`. 이미 그 상태면 409 `unchanged`. 기존 Task는 그대로이고, 그 서버에 새 Task를 두는 계획은 `NODE_CORDONED`. `uncordon-node`는 `control.NodeSelection{ID}`. `GET /nodes` 행에 `cordoned`·`cordonReason`·`cordonedBy`(막은 사용자 이름)·`cordonedAt`(RFC 3339, REQ-50). uncordon하면 셋 다 빠진다. 이벤트 `node-cordoned`·`node-uncordoned`.
- 서버 격리·복귀(시스템 관리자, UI-12 머리 단추): `POST /nodes/{node}/isolate`·`POST /nodes/{node}/restore` `{opId, operation?, epoch?, expected?}` → `isolate-node`·`restore-node`. 본문과 기본값은 아래 서버 제거와 같고, operation 기본값은 `isolate-<opId>`·`restore-<opId>`다. 이미 격리된 서버의 격리, 격리되지 않은 서버의 복귀, 제거된 서버는 409 `unchanged`. `POST /ops`로 `{Node}`를 보내던 옛 방식은 이제 거절된다(실제 payload는 `NodeLifecycleChange`).
- 서버 제거(시스템 관리자, UI-12 '서버 제거…'): `POST /nodes/{node}/remove` `{opId, operation?, epoch?, expected?}` → `remove-node`(`control.NodeLifecycleChange{ID, Operation, Epoch}`, `mydc node remove`와 같다). operation은 노드 작업 ID(영소문자·숫자·`-`, 영소문자로 시작, 63자)이고 기본값은 `remove-<opId>`다. epoch 기본값은 `members`의 노드 작업 epoch, expected 기본값은 서버 `revision`이다. 없는 서버는 404, 이미 제거된 서버는 409 `unchanged`. 마지막 투표 서버·과반 상실·진행 중인 노드 작업 같은 거절은 mydcd가 판단해 op 결과로 온다. 누르기 전 확인 창은 `GET /nodes/{node}/remove-plan`(REQ-52, `node-remove-plan`)을 읽는다 → `{node, epoch, expected, removable, blockers:[{code, detail?}], votersBefore, votersAfter, quorumAfter, faultToleranceAfter, tasks:[{tenant, app, service, task, node, standalone?, target?, generation, revision, movable, reason?}], storage:[{id, path, generation, revision, volumes, retained, draining, closed}], volumes:[{tenant, app?, id, fixed, retained, generation, move?}], activity:{resources, flows, writers, leases, cdJobs}, nativeClosed, pendingOperation?}`. blockers의 code는 `remove-node`가 거절할 때의 mydcd 거절 사유다(`LAST_VOTER`·`QUORUM_LOSS`·`SELF_REMOVAL`·`NODE_OPERATION_PENDING`·`FIXED_VOLUME_PRESENT`·`NODE_STORAGE_NOT_DRAINED` 등). 거절된 op는 `state: failed`와 그 `errorCode`로 보인다. 예전의 task `instance`·storage `bytes`·`drained`는 없다(각각 `task`, `closed`). 없는 서버는 404.
- 서버 고급 관리(REQ-51, RQ12 실제 모양, 시스템 관리자, UI-12 '고급 ▾'). 계획과 거절은 모두 mydcd의 것이다. 비우기·강제 제거 계획은 읽을 때마다 시각·probe가 달라지므로, 웹은 계획이 말하는 내용(시각·읽은 위치·probe 제외)의 digest를 `plan`으로 준다. 보낼 때 같은 `operation`으로 계획을 다시 읽고, `plan`이 같을 때만 새로 읽은 계획으로 서명한다. 다르면 409 `plan-changed`. operation은 노드 작업 ID 문법이고 아니면 422다. 계획 읽기에 `?operation=`을 주지 않으면 웹이 `drain-…`·`force-…`(12 hex)를 정해 응답에 싣는다. 그 값을 보낼 때 그대로 돌려준다.
  - 비우기: `GET /nodes/{node}/drain-plan?operation=` → `{node, operation, expected, plan, code?, blockers, tasks(위 task 모양), jobs:[{tenant, app, operation, target, services, tasks(수), moveVolume}]}`. task의 reason은 `FIXED_VOLUME`·`NO_TARGET` 등이다. `POST /nodes/{node}/drain` `{opId, plan, operation, leaveBlocked?}` → `drain-node`(`control.NodeDrainChange`, Expected는 계획의 expected). 못 옮기는 Task가 있으면 `leaveBlocked: true`가 있어야 한다(없으면 mydcd가 거절한다). 진행은 `GET /nodes/{node}/drain-status?operation=` → `{node, operation, state, total, moved, blocked, jobs:[{tenant, app, operation, state, total, moved}]}`. operation을 빼면 mydcd가 그 서버의 진행 중(없으면 가장 최근) 비우기를 누가 시작했든 준다. 비우기 기록이 없으면 404다. 시스템 관리자의 `GET /nodes` 행에는 같은 조회로 채운 `drain?:{operation, state}`가 붙는다. mydcd members 행에는 비우기가 없어서 데몬이 그 쪽 서버마다 operation 없는 status를 한 번씩 묻는다. 기록이 없거나 읽지 못하면 붙지 않는다. `pendingOperation`에는 drain operation이 오지 않는다. 이벤트 `node-drained`.
  - 투표 서버에서 내리기: `GET /nodes/{node}/voter-plan`(`node-demote-plan`) → `{node, epoch, expected, demotable, code?, blockers, votersBefore, votersAfter, quorumAfter, faultToleranceAfter, quorum, tolerates, pendingOperation?}`. `quorum`·`tolerates`는 예전 이름으로 quorumAfter·faultToleranceAfter와 같다. code는 첫 거절 사유이고 없으면 내릴 수 있다. `POST /nodes/{node}/demote` `{opId, expected?}` → `demote-node`(`control.NodeSelection{ID}`, expected 기본값은 계획의 expected).
  - 노드 신원 교체: `POST /nodes/{node}/rotate-identity` `{opId, operation?, expected?}` → `rotate-node-identity`(`control.NodeIdentityChange{ID, Operation}`, operation 기본값 `rotate-<opId>`, expected 기본값 서버 행의 `joinRevision`(멤버 항목 revision, `mydc node rotate-key`와 같다)).
  - 진단 묶음: `GET /nodes/{node}/diagnostics`(`node-diagnostics`) → `application/gzip` 내려받기. 헤더는 `Content-Disposition: attachment; filename="mydcd-diag-<node>-<만든 시각>.tar.gz"`, `X-MyDC-Created-At`, `X-MyDC-Digest`(sha256 hex), 잘렸으면 `X-MyDC-Truncated: true`다. 상한은 압축 64 KiB(풀면 128 KiB)다. 웹은 digest·상한을 확인한 뒤 mydcd 묶음을 그대로 넘기고, 저장하거나 내용을 로그에 남기지 않는다. 맞지 않으면 502 `bad-bundle`.
  - 강제 제거: `GET /nodes/{node}/force-remove-plan?operation=`(`node-force-remove-plan`, mydcd가 그 서버에 probe를 보낸다) → remove-plan 모양 + `{operation, forceable, code?, plan, probe?:{responding, startedAt, finishedAt}}`. 응답하는 서버나 진행 중인 노드 작업이 있으면 code가 붙고 `forceable: false`다. `POST /nodes/{node}/force-remove` `{opId, plan, operation}` → `force-remove-node`(`control.NodeForceChange{ID, Operation, Epoch, Probe}`, Expected는 계획의 expected). probe가 없으면 409 `not-forceable`. 그 서버 Task는 `missing`이 되고 이벤트 `node-removed`.
- 터널 다시 연결 (RQ4, docs/reference/tunnel-reconnect.md): `GET /t/{t}/networks/{name}/tunnels` → `{items:[{tenant, network, pairId, from, to, state(up/degraded/down/pending), since}]}`. mydcd에 망별 링크 읽기가 없어서, 망 행의 서버 목록과 `mesh-links` 행(이 작업 공간 보기)을 PairID(정렬한 `a/b`)로 묶는다. `since`는 mydcd가 작업 공간 보기에 양쪽 관측값을 주지 않으므로 0이다. 다시 연결 횟수는 더 주지 않는다. `POST /t/{t}/networks/{name}/tunnels/reconnect` `{opId, from, to}`와 `POST /nodes/{node}/tunnels/{peer}/reconnect` `{opId}`는 같다. `from`(node)이 다이얼하는 쪽이고 `to`(peer)가 상대다. 먼저 `tunnel-reconnect-plan {Node, Peer}`을 읽고, `reconnect-tunnel` `control.TunnelChange{Operation:"op-"+opId, Plan}`(Expected 0)에 서명한다. 시스템 관리자만 되고 판단은 mydcd가 한다. 링크가 down이 아니거나 활성 멤버가 아니면 409 `not-down`. op가 `applied`면 작업이 접수된 것이다. 진행은 `GET /tunnel-reconnects/{operation}` → `{operation, user?, state(queued/running/done/failed), node, peer, pairId, at, revision, result?(reconnected/already-connected/failed), code?, error?, handshakeAt?(Unix ms), keptExisting?}`로 본다. 모르는 operation은 404.
- 서버 이미지 캐시 정리(시스템 관리자, [node-image-cache](../node-image-cache.md)): `GET /nodes/{node}/image-prune-plan` → `{node, images:[{ref, aliases, digest, bytes}], bytes, plan, remaining, inUse, total}`. 데몬이 mydcd `image-cache-plan` 목록(8개씩)을 모두 읽어, 컨테이너도 공유 참조도 없는 미사용 이미지 중 앞의 8개를 다음 정리 대상으로 보여 준다(`digest`는 전체 이미지 ID, `ref`는 첫 별칭이고 없으면 빈 값). `remaining`은 이번에 못 넣은 미사용 이미지 수, `inUse`는 쓰는 중이라 남기는 이미지 수다. `bytes`는 Docker가 알린 크기의 합이고 실제 회수량이 아니다. 예전의 `lastUsed`는 mydcd에 없다. `POST /nodes/{node}/image-prune` `{opId, plan}` → `prune-node-images`(`imagecache.Change{Operation: "op-"+opId, Plan}`, Expected 0). 데몬이 대상을 다시 읽고 그 ID들만 고른 계획을 mydcd에서 새로 받는다. 대상이 바뀌었거나 하나라도 쓰이기 시작했으면 409 `plan-changed`. op `applied`는 접수일 뿐이고 진행은 `GET /image-prunes/{operation}` → `{operation, user, state(queued/running/done/failed), node, at(Unix 초), revision, images(선택 ID), parts:[{digest, state(removed/already-absent/failed/skipped), code?, error?, at}]}`. 없는 작업은 404. 8개보다 많으면 정리를 다시 한다.
- 그 밖의 임시 조치는 이미 있는 끝점이다: Task 하나 재시작(`task/restart`), 자동 배포 정지·재개(`cd/pause`·`cd/resume`), 저장소 정지·시작, 직전 버전 되돌리기(배포).
