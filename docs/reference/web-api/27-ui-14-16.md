## 서버 저장 경로와 작업 공간 서버 한도 (UI-14·16, 시스템 관리자)

공유 자원 만들기와 같은 길이다: 데몬이 sfcd 페이로드를 만들고 `control.InputChange`를 거쳐 서명 → 저장 → 보내기, 응답은 `{op}`, 같은 `opId`·같은 본문은 저장된 op, 다른 본문은 409 `op-conflict`, 칸이 틀리면 서명 전에 422 `invalid`. 모두 sfcd의 시스템 관리자(ManageCluster) 작업이라 다른 사람은 op가 `failed`(forbidden)다. 서버 키·소유 키는 sfcd가 채운다.

| 끝점 | 본문 → action |
|---|---|
| `POST /nodes/{node}/storage` | `{opId, id([a-z][a-z0-9-], 63자까지), path(절대·정리된 경로, "/" 아님), tenants:[작업 공간 id], allTenants?, capacityBytes?(0 = 한도 없음)}` → `add-node-storage`(`nodestorage.Definition`, Expected 0). tenants는 데몬이 정렬하고 겹친 것을 뺀다. allTenants와 tenants를 함께 주면 422. 같은 서버의 다른 저장 경로 안이나 위면 op `failed` |
| `PATCH /nodes/{node}/storage/{id}` | `{opId, addTenants?, removeTenants?, allTenants?, capacityBytes?, expected}` → `set-node-storage-policy` `{Node, ID, AddTenants?, RemoveTenants?, AllTenants?, CapacityBytes?}`. 바뀌는 것만 보낸다. 모두 비면 422. `expected`는 행의 `revision`. 이미 허용된 작업 공간을 더하거나 없는 것을 빼면, 꺼내는 중이면, 모든 작업 공간 허용 중에 목록을 고치면, 또는 용량 한도가 이미 예약된 합보다 작으면 `failed` |
| `POST /nodes/{node}/storage/{id}/drain` | `{opId, expected}` → `drain-node-storage`. 새 볼륨을 막는다. 서버가 닫았다고 알리면 행이 `closed:true`가 되고 `revision`이 또 오른다 |
| `DELETE /nodes/{node}/storage/{id}` 또는 `POST …/remove` | `{opId, expected}` → `remove-node-storage`. `draining`·`closed`이고 등록된 볼륨이 0개일 때만 된다(아니면 `failed`). 데이터는 지우지 않는다 |
| `PUT /t/{t}/limits/{node}` | `{opId, cpus(코어, 소수 가능), memoryBytes, expected}` → `set-node-quota`(`tenancy.NodeLimit`). `expected`는 이 작업 공간 한도 행의 `revision`(새로 만들면 0). cpus는 데몬이 `Capacity.CPU` 단위(코어당 10^9)로 바꾼다. 화면이 안 바꾸는 칸(망 수, 소비자 수, 패킷·외부 접속 한도)은 지금 한도의 값을 그대로, 새 한도면 서버 전체 한도의 값을 쓰고, 어느 쪽이든 서버 전체 한도를 넘지 않게 맞춘다. 서버 전체 한도가 없거나 cpus·memoryBytes가 그것보다 크면 422 `limit-over-node`, `error.max: {cpus, memoryBytes}`(전체 한도가 없으면 0, 0)이고 저장하지 않는다. 사용량이 새 한도보다 크면 sfcd가 거절한다(`failed`) |

`GET /t/{t}/resources`의 한도 행(`limit`)에는 서버 전체 한도 `nodeCpus`·`nodeMemoryBytes`가 붙는다. 서버 전체 한도는 시스템 관리자만 읽으므로 다른 사람에게는 없다. 한도 행에는 `networks`·`maxConsumers`·패킷·외부 접속 한도 칸도 있다.
